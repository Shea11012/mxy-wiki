# 多智能体架构与框架

> Multi-Agent 不是“多写几个角色 Prompt”，而是多个自治执行上下文通过明确协议、状态和所有权协作。只有当并行性、隔离、权限边界或专业化带来可测收益时，它才优于单 Agent。

## 一、先判断是否真的需要多个 Agent

适合：

- 子任务可以并行，且结果合并成本低
- 不同任务需要隔离上下文、工具或权限
- 需要独立 verifier/reviewer 降低同一轨迹偏差
- 单个上下文无法容纳各领域工作集
- 需要故障隔离或不同 SLA/模型配置

不适合：

- 任务强顺序依赖、共享写状态频繁
- 角色只是不同 system prompt，没有独立状态或能力
- 没有可靠 grader，无法判断多个答案谁更好
- 协调 token、延迟和冲突超过并行收益

应先建立同模型、同预算的单 Agent baseline，再证明多 Agent 的任务成功率或延迟收益。

## 二、常见拓扑

| 模式 | 数据流 | 优点 | 主要风险 |
|------|--------|------|----------|
| Pipeline | A → B → C | 简单、易审计 | 上游错误级联、串行延迟 |
| Supervisor/Hub-Spoke | Hub 分解与汇总，Workers 执行 | 统一控制、可并行 | Hub 瓶颈、错误分解 |
| Hierarchical | Supervisor → Orchestrator → Worker | 适合大规模分层 | 协议和状态复杂 |
| Blackboard | Agent 读写共享工件/状态 | 松耦合、异步 | 冲突、脏读、责任不清 |
| Map-Reduce | 并行 map → reducer | 文档/候选可分片 | reducer 丢失细节 |
| Debate/Vote | 多候选 → 比较/投票 | 增加方案覆盖 | 相关错误、迎合、成本高 |
| Market/Queue | Agent 认领任务 | 动态扩缩容 | 重复认领、饥饿、租约失效 |

Multi-Agent 是横向编排维度；每个子 Agent 内部仍可使用 Tool-Calling Loop、Plan-and-Execute 或 Reflection。

## 三、通信与状态

不应默认共享完整消息历史。更稳妥的消息信封：

```text
task_id / correlation_id
sender / recipient
intent / schema_version
input_refs / artifact_refs
constraints / permissions
expected_output_schema
deadline / budget
attempt / idempotency_key
```

### 单一事实源

- Task store 保存任务状态、依赖和所有权
- Artifact store 保存报告、patch、测试结果等大对象
- Event log 保存不可变事件
- Agent 本地上下文只是缓存或工作集，不是全局事实源

Blackboard 需要 version/CAS、锁或 CRDT 等冲突策略；消息队列需要 ack、visibility timeout、dead-letter queue 和幂等消费者。

## 四、任务生命周期

```text
created → ready → leased/running → verifying → completed
                     ├→ retryable_failed → ready
                     ├→ blocked
                     ├→ cancelled
                     └→ terminal_failed
```

关键机制：

- 依赖 DAG 和 ready 条件
- lease/heartbeat 防止 worker 死亡后任务永久占用
- attempt 上限、退避和 dead-letter
- 输出 schema 与 completion criteria
- verifier/quality gate
- 人工审批、取消和接管
- 每个任务的 token、时间、工具和费用预算

## 五、冲突与合并

### 代码任务

- 每个 Agent 使用隔离 worktree/容器
- 明确文件或模块所有权，尽量避免多写入者
- 合并前重放基线测试、类型检查和安全扫描
- 冲突由专门 merger 或人处理，而不是让多个 Agent 同时改主工作区

### 知识任务

- 保留每个 claim 的来源和作者 Agent
- Reducer 不只总结，也要识别冲突、缺证据和覆盖缺口
- 投票不能替代事实验证；多个 Agent 可能共享同一训练偏差和错误来源

## 六、框架定位（2026-07 快照）

框架 API 变化快，以下是定位而非永久版本承诺：

### Microsoft AutoGen / Microsoft Agent Framework

AutoGen 曾以 `ConversableAgent`、AgentChat、GroupChat/GraphFlow 等多 Agent 对话抽象著称。Microsoft 当前官方路线已提供 **Microsoft Agent Framework**，并发布从 AutoGen 和 Semantic Kernel Agent Framework 的迁移指南。因此新项目选型时不能只依据旧版 AutoGen Notebook；应评估当前 Agent Framework，同时把旧课程视为架构教学样例。

官方锚点：

- <https://learn.microsoft.com/en-us/agent-framework/overview/>
- <https://learn.microsoft.com/en-us/agent-framework/migration-guide/from-autogen/>

### CrewAI

CrewAI 以角色/任务的 **Crews** 和事件/状态驱动的 **Flows** 为主要抽象。适合快速表达团队与业务流程，但生产能力仍取决于状态持久化、幂等、观测、权限和评测，不能由 `role/goal/backstory` 自动获得。

官方锚点：<https://docs.crewai.com/>

### LangGraph

LangGraph 是低层状态图与 Agent orchestration runtime，核心价值是状态、循环、持久化/durable execution、streaming 和 human-in-the-loop；它不是专门的“多 Agent 框架”，单 Agent 长流程同样适用。

官方锚点：<https://docs.langchain.com/oss/python/langgraph/overview>

## 七、框架选型

不要使用固定的“学习曲线低/灵活性中”表格代替 PoC。应比较：

| 维度 | 要问的问题 |
|------|------------|
| 控制模型 | 对话、图、workflow 还是 queue？是否匹配任务 |
| 状态 | checkpoint、恢复、迁移和并发一致性如何实现 |
| 协议 | 输出 schema、工具、MCP/A2A 或自定义消息如何接入 |
| HITL | 能否安全暂停、审批、修改状态并恢复 |
| 运维 | trace、metrics、部署、租户、限流和成本是否可控 |
| 安全 | 身份、权限、secret、沙箱和审计边界在哪里 |
| 锁定 | 状态和任务定义能否脱离框架迁移 |
| 评测 | 能否重放 trace，并与单 Agent baseline 做同预算比较 |

## 八、评测

除最终成功率外，应记录：

- 各任务/Agent 的成功率与失败位置
- 关键路径延迟、并行加速比和队列等待
- token、调用数和总成本
- 重复工作、消息数量、冲突与重试
- supervisor 路由准确率和 verifier 误判
- worker crash、超时、消息重复/乱序下的恢复
- 权限越界、Prompt injection 横向传播和数据泄漏

> 多 Agent 的目标不是让系统“看起来像团队”，而是在可测约束下改善吞吐、隔离、质量或可靠性。
