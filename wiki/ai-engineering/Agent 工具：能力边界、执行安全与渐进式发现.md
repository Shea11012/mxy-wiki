# Agent 工具：能力边界、执行安全与渐进式发现

> 本页是《AI Agents in Depth — Design Principles and Engineering Practice》第四章“工具”的学习型 source-summary。原始 Clipping 已保存为不可变来源：`raw/2026/08/19/工具.md`。
>
> 摘录：Agent 主动获取信息、感知世界的方式

## 1. 核心命题：工具是 Agent 的世界接口

Agent 的工具不是把若干 API 端点机械暴露给模型，而是连接模型与真实数字世界的“手脚和感官”。模型通过工具获取信息、改变外部状态、驱动其他 Agent 或人类，并在异步事件到来时被唤醒。

本文真正讨论的是工具契约和能力边界：模型什么时候应调用工具、工具不能做什么、参数如何保持原样传递、执行后如何验证、失败和取消意味着什么，以及工具数量增长后如何被发现。

可以把一次可靠的工具工作流表示为：

```text
任务需求
  -> 发现合适能力
  -> 准确构造参数
  -> 通过权限与安全门控
  -> 执行操作
  -> 验证结果并审计
  -> 根据反馈继续、重试、升级或停止
```

这与 [[MCP 工具设计：让 Agent 更准确]] 关注的名称、描述、Schema、输出和错误反馈互补：前者扩展到工具运行时和发现机制，后者更集中于工具定义本身。

## 2. 五类工具：按调用方向和作用对象理解

| 工具类型 | 调用方向 | 作用对象 | 典型问题 |
| --- | --- | --- | --- |
| 感知工具 | Agent 主动调用 | 获取信息 | 如何控制输出量和信息损失 |
| 执行工具 | Agent 主动调用 | 改变世界 | 如何限制副作用和权限 |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent 或人类 | 如何定义职责、生命周期和消息协议 |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 | 用户不在线时如何异步触达 |
| 事件触发工具 | Agent 注册、外部触发 | 驱动 Agent 开始执行 | 如何跨会话接入事件和唤醒 |

> 摘录：外部世界驱动 Agent 行动的方式

前三类主要是 Agent 主动调用的工具；事件触发和用户沟通则依赖事件驱动的异步运行时。事件触发至少包含两个时刻：Agent 注册自己关心的事件，之后由外部系统回调并唤醒 Agent。没有这类能力，Agent 只能在用户发消息时被动响应。

“感知”和“执行”是最重要的一条工程分界：感知工具主要影响模型看到什么，执行工具会改变外部世界。前者通常可以缓存、并行和安全重试，后者必须明确权限、副作用、取消和幂等语义。

## 3. 能力应该表达成专用工具还是 Skill

### 3.1 两种表达形态

**专用代码工具**使用结构化函数调用，参数 schema 可以表达类型、枚举、范围和联合约束；它确定性强、便于测试和审计，但每个工具都要占用描述 token，工具数量增长会增加模型选择负担。

**Skill + 通用执行器**用自然语言描述操作流程，让 Agent 通过终端或代码解释器执行。例如部署 Skill 可以描述构建、打包和应用部署的步骤，不必为每个步骤分别注册工具。它用少量通用工具覆盖更多变化场景，维护自然语言流程也比修改代码、测试和部署专用工具轻。

### 3.2 三维选择框架

| 判断维度 | 更适合专用工具 | 更适合 Skill + 通用执行器 |
| --- | --- | --- |
| 参数复杂度 | 嵌套对象、多字段联合校验、复杂类型约束 | 参数简单、CLI 能清楚表达 |
| 变更频率 | 稳定的底层操作 | 经常变化的流程和编排 |
| 模型能力 | 弱模型需要 schema 引导 | 强模型能理解流程并生成命令 |

Skill 不是专用工具的全面替代。它把一部分约束从结构化接口转移到自然语言、命令生成和运行环境中，因此会增加转义错误、平台差异和命令误用风险。高权限、复杂参数和不可逆操作仍应优先使用专用工具。

### 3.3 粒度与通用性

工具粒度过细会导致工具数量激增，增加选择负担；粒度过粗则会让一个接口拥有模糊或过于复杂的语义。整合工具的核心标准是功能相似性和使用场景重叠度。例如，多个文档格式都执行“从已知路径读取文档文本”，可以整合为 `read_document(file_type)`。图片 OCR 和视频关键帧提取虽然都属于内容提取，但参数形态、延迟特征和输出语义差异很大，不应强行合并。

工具应尽可能通用，但安全、权限和性能是明确的例外。沙盒里的代码解释器可以覆盖许多计算场景；生产数据库写操作则应使用专用接口，以提供细粒度权限、校验和审计。

## 4. 工具描述与参数保真

### 4.1 描述应支持调用决策

工具描述不应只回答“它能做什么”，还应回答：

- 什么时候使用；
- 什么时候不要使用；
- 接受和拒绝哪些输入；
- 成功返回什么；
- 失败如何修正；
- 调用需要多长时间或消耗什么资源。

> 摘录：工具描述的核心是让 LLM 知道“什么时候用”

例如，文件搜索工具应明确它只能基于文件名匹配，不能搜索文件内容。参数应使用具体示例说明 RFC3339、E.164 等格式，而不是只丢给模型一个抽象术语。返回值也应写出字段结构和分页、截断或耗时行为。工具选择频繁出错时，优先检查描述、边界和反例，不要一开始就更换模型。

### 4.2 模型看到的输入必须等于工具实际收到的输入

文章用静默转换弯引号、静默追加命令参数说明了一个基础原则：

> 摘录：模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差

如果参数传递层把模型传入的字符偷偷改变，模型根据读取结果构造的替换参数就可能永远匹配失败；如果工具在命令后偷偷追加参数，模型即使反复修改自己的调用也找不到真正失败原因。

因此，工具层不得在模型不知情的情况下修改输入或输出。如果确实需要规范化，应在工具描述中说明，并在返回值中告知最终执行的参数或规范化结果。

## 5. MCP：统一互操作，不等于完整运行时

MCP 采用客户端—服务器架构：Server 暴露能力，Client 通常是 Agent 框架、IDE 或其他宿主。它标准化工具描述和 JSON Schema，也区分可执行工具、只读资源和可复用提示模板；本地可以使用 stdio，远程可以使用 Streamable HTTP。

MCP 的主要价值是互操作：工具开发者不必针对每个 Agent 框架重复适配。但它不自动提供跨会话、多事件源、离线唤醒的完整事件运行时。MCP 负责能力调用标准化，Agent 框架仍需负责事件接入、调度、并发和唤醒。

因此要区分两个独立问题：

```text
是否采用 MCP 作为互操作协议？
是否在会话开始时暴露全部 MCP 工具定义？
```

前者可以是“是”，后者不一定。工具定义过多时，可以用目录、代理工具、动态发现或 Skills 做延迟披露。

### 5.1 MCP 的信任边界

接入第三方 Server 相当于把其工具描述注入模型上下文，通常还要交给它某些凭证。主要风险包括：

- **工具描述投毒**：description 夹带提示注入；
- **恶意或被劫持的 Server**：更新或供应链环节改变行为；
- **同名工具遮蔽**：相似工具把调用导向不可信来源；
- **凭证滥用**：模型被诱导把 OAuth token 或 API key 用于非预期操作。

基本防线是审查 description、锁定版本、升级时重新审查、为每个 Server 使用最小权限和有期限凭证，并在运行时对结构化工具调用进行独立安全审查。MCP 是能力互操作层，不替代策略引擎、权限系统和审计系统。

## 6. 感知工具：控制信息量、完整性和形态

搜索工具应返回结构化候选列表，而不是把所有全文直接拼入上下文。结果较多时使用分页或游标，并返回总数、当前范围和继续获取下一页的方法，让 Agent 自己决定是否深入读取。

读取工具应支持 `offset/limit`。超过阈值时可以截断，但必须显式说明：已经展示哪些内容、总量是多少、遗漏了多少、如何继续读取。静默截断会让 Agent 误以为自己掌握了完整信息。

感知工具的只读特性带来两个工程红利：相同查询可以缓存，多个互不依赖的感知调用可以并行执行。执行工具则不能直接套用这种自由，因为调用顺序和副作用需要严格控制。

### 6.1 多模态感知的三条路线

| 路线 | 优点 | 代价和边界 |
| --- | --- | --- |
| 原生多模态 | 直接保留布局、图表和空间关系，能力上限高 | 消耗更多 token，依赖主模型支持 |
| 提取为文本 | 文字主导文档成本低、上下文紧凑 | 丢失版式、图表和空间结构 |
| 工具化分析 | 主模型按问题调用专门多模态模型，结果可压缩 | 一次端到端深度理解可能不如原生模式 |

纯文字文档适合文本提取；UI、复杂表格和设计稿等布局敏感内容应保留图像或使用多模态分析工具。

## 7. 执行工具：从能力开放到受控副作用

### 7.1 层次化安全防护

第一层是输入验证：检查路径遍历、命令注入、数据类型和格式，发现异常时快速失败，不尝试“智能修正”。第二层是权限控制：限制工作目录、网络、命令、API 配额和速率。黑名单只能作为基础层，不能作为唯一防线，因为命令可以通过不同写法绕过表面匹配；更健壮的方案需要理解命令实际意图。

第三层是独立审查。对于不可逆操作，可以让一个模型提出行动，另一个独立模型审批；审批拒绝应作为工具调用失败和修正建议进入 Agent 轨迹，而不是简单地无限重试。

### 7.2 提议者—审核者与 Sidecar

**提议者—审核者**主要审查开放式行动的合理性，适合收费、发邮件、修改关键配置和创建外部资源等高影响操作。事后验证时应尽量切换模态：渲染文档后检查截图，修改配置后在沙盒里实际运行。

**Sidecar**主要在工具执行前对结构化调用做实时门控：

```json
{
  "tool": "bash",
  "command": "rm -rf /tmp/data"
}
```

它不读取主模型自由文本中的理由，避免网页或用户输入中的提示注入影响审核判断。Sidecar 处理的是相对简单的安全分类，因此可以使用轻量模型；提议者—审核者审查开放式计划，需要更接近的能力水平。连续拒绝时应熔断并回退到人工判断。

### 7.3 执行—验证—反馈

> 摘录：如果操作结果可以被验证，就应该自动验证

写文件不应只返回“成功”，而应立即运行对应语言的语法检查或 linter，把结构化错误返回给 Agent。这样工具调用不只是改变世界，还会把验证结果重新送入下一轮决策，形成：

```text
执行 -> 验证 -> 反馈 -> 修正或继续
```

长输出应保存完整结果，只把头尾和省略提示放入上下文，例如说明省略了多少行、完整文件在哪里、可以使用什么读取工具继续查看。

### 7.4 隔离与可观测性

venv 只隔离包依赖，不是安全沙盒。进程级隔离适合低风险本地开发；容器提供更强的文件系统和网络隔离，但仍共享宿主机内核；microVM 或虚拟机提供更强的隔离，适合不可信代码。无论选择哪一级，都应限制 CPU、内存、磁盘和网络资源。

执行工具还需要记录调用时间、参数、结果、耗时、调用者上下文和审计原因，并统计成功率、失败率、超时和资源超限，以便监控、调试和追责。

### 7.5 超时、取消和幂等

超时或取消不代表副作用一定没有发生。转账请求超时后，钱可能已转出但响应丢失；Agent 直接重试可能造成重复转账。

可幂等操作可以携带唯一标识，由服务端去重；也可以在重试前先查询目标状态。不可幂等的邮件、电话和转账等操作，应采用两段式：

```text
预检与预演
  -> 返回结果和确认令牌
  -> 用户或策略确认
  -> 凭令牌执行一次
```

执行阶段失败后不能就地盲目重发，而应重新查询并回到预检流程。

## 8. 协作工具与 HITL

子 Agent 的核心价值是专业化分工。每个子 Agent 可以有独立的模型、工具集、提示词和知识库，但主 Agent 必须清楚声明：角色、上下文来源、任务边界和输出格式。

上下文来源应显式区分，例如：

- `[FROM_MAIN_AGENT]`：主 Agent 的任务指令；
- `[FROM_USER]`：用户补充的信息；
- `[TOOL_RESULT]`：工具执行结果。

这类标记不能单独提供安全保证，但能减少子 Agent 把工具结果或外部文本误读为上级指令的风险。

协作接口可分为：

1. 启动和取消；
2. 运行中消息传递；
3. Agent 发现和状态查询；
4. 结果获取。

它们可以承载同步、异步、流式和多轮交互。任务失去意义时及时取消，能够减少无效计算和 token 消耗。

HITL 请求需要超时、保守默认行为、优先级队列和多渠道通知。人类的批准、拒绝及理由不只是一次性控制信号，也可以形成反馈闭环：稳定原则进入知识库或 Skill，隐含偏好可以形成后训练数据。

## 9. 主动工具发现与渐进式披露

当工具从十几个增长到数百或数千个时，全量 schema 注入会占用上下文、降低选择精度，并干扰模型决策。仅按初始用户请求做一次性语义预筛也不够，因为执行过程中才可能出现跨领域的能力缺口。

主动发现的基本流程是：

```text
Agent 声明当前能力缺口
  -> 按服务器级定位能力组
  -> 在服务器内匹配具体工具
  -> 动态注入 schema
  -> 调用工具
```

如果候选相似度低于阈值，应明确返回“未找到”，让 Agent 改写需求、使用基础工具，或考虑创造新工具。动态 schema 的加载还要考虑 KV Cache：把新定义追加到轨迹末尾，保持静态前缀稳定，并让已加载定义固定在初次注入的位置。

### 9.1 Skills 作为按需查阅

Skills 不把所有工具的正式 schema 常驻上下文，而是在启动时只提供名称和简短描述。模型需要某能力时，使用通用文件读取能力查阅对应 Skill，再按引用读取脚本和子文档。这类似人查阅工具书或维基百科，把工具发现转化为渐进式知识查阅。

Skills 的优点是人类容易编写和维护，不需要额外的嵌入索引；代价是模型需要自己生成命令并处理引号、转义和平台差异。参数复杂的能力仍适合原生工具 schema；也可以让模型先把复杂参数写成 JSON 文件，再由 CLI 导入。

因此：

> 摘录：MCP 解决的是 **互操作** （一次开发，处处可用）

二者可以组合：MCP 作为底层互操作协议，Skills 或代理工具负责能力组织和渐进式披露。
