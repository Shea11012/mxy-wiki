# 缓存升降级

在 Redis 故障需要降级，或恢复后需要升级的混合访问期间，如何保证强一致性。
方案来自 DTM/rockscache 的缓存一致性体系。

> [!note] 前置知识
> 本文基于 [[DTM 缓存一致性方案]] 中的标记删除机制。升降级是强一致模式下的特殊场景。

## 为什么需要特殊处理

> 摘录：上述的强一致方案中，说明了其强一致的前提是：“所有的数据读取，只能够由缓存”。不过如果Redis如果发生故障，需要进行降级

降级期间缓存与 DB 混合读取，打破了「所有读取只走缓存」的前提，需要额外策略保证一致性。

## 混合访问的一致性策略

> [!warning] INFERRED — 以下为推理结论
> 混合访问策略：使用分布式事务保证原子操作——将缓存标记为"锁定中"，更新DB，去除锁定标记并标记删除。
> 源文锚点：raw/2026/05/31/dtm缓存一致性.md 第 249-254 行

使用 SAGA 事务保证原子性（因为更新 DB 是可能失败的业务操作）。读取逻辑不变：
- 标记为"锁定中"的数据 → 睡眠等待后重读
- 标记删除的数据 → 不返回旧数据，等新数据完成后返回
- 读 DB → 直接读取，无额外操作

## 升降级顺序（必须严格遵守）

> 摘录：升降级的开启关闭有顺序要求，不能够同时开启缓存读和写，而是需要在开启缓存读的时候，所有的写操作都已经确保会更新缓存

### 降级：先降读，再降写

| 阶段 | 读 | 写 |
|---|---|---|
| 初始状态 | 混合读（部分缓存+部分DB） | 写 DB + 缓存 |
| ① 读降级 | **全部 DB 读** | 写 DB + 缓存（不变） |
| ② 写降级 | 全部 DB 读（不变） | **只写 DB** |

### 升级：先升写，再升读

| 阶段 | 读 | 写 |
|---|---|---|
| 初始状态 | 全部 DB 读 | 只写 DB |
| ① 写升级 | 全部 DB 读（不变） | **写 DB + 缓存** |
| ② 读升级 | **混合读（部分缓存+部分DB）** | 写 DB + 缓存（不变） |

> [!important] 顺序不可颠倒
> **降级**：如果先降写再降读，在降写完成但降读未完成的窗口期，读仍走缓存但写已不更新缓存，可能读到旧数据。
> **升级**：如果先升读再升写，读开始走缓存但写还没参与缓存更新，缓存可能返回过期数据。

## 适用场景

- Redis 集群故障切换期间
- Redis 维护窗口期
- 网络分区导致缓存不可达时
- 配置中心下发降级/升级指令的过渡期

需要配合 DTM 的 SAGA 事务保证升降级过程中 DB 与缓存操作的原子性。
