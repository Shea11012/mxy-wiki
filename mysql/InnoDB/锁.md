# InnoDB 锁机制

> 加锁的基本单位是 **next-key lock**，所有退化规则都基于此展开。

---

## 1. 全局锁

对整个数据库加锁，多用于全库备份。

```sql
FLUSH TABLES WITH READ LOCK;
```

该命令会导致 DDL、DML 语句不能执行。可以使用 `mysqldump --single-transaction` 启动事务拿到一致性视图来替代。

释放全局锁：`UNLOCK TABLES`。

---

## 2. 表级锁

### 2.1 表锁

显式锁定整张表：

```sql
LOCK TABLES t READ;   -- 读锁，其他会话可读不可写
LOCK TABLES t WRITE;  -- 写锁，其他会话不可读写
```

### 2.2 元数据锁（MDL）

对表执行操作时 **自动加** 的锁，用于防止 DML 执行期间表结构被变更：

- CRUD 操作 → 加 **MDL 读锁**
- 表结构变更（ALTER 等）→ 加 **MDL 写锁**

> [!warning] MDL 写锁的优先级高于读锁
> 申请 MDL 锁的操作会形成队列，写锁获取优先级高于读锁。一旦出现 MDL 写锁等待，会阻塞后续该表的**所有** CRUD 操作。

### 2.3 意向锁（Intention Lock）

在对表中**行**加 S/X 锁之前，需要先在**表级别**加上意向锁：

- 行级共享锁 → 表级 **意向共享锁（IS）**
- 行级独占锁 → 表级 **意向独占锁（IX）**

**核心规则**：

> 意向锁之间兼容，意向锁与行锁之间兼容，**意向锁只与表级共享锁/独占锁冲突**。

**存在理由**：如果没有意向锁，加表锁时就需要遍历所有行来检查是否有行锁——这在数据量大的场景下是不可接受的。意向锁使得加表锁时只需检查表级的意向锁即可。

### 2.4 AUTO-INC 锁

自增主键的锁机制。向 `AUTO_INCREMENT` 列插入数据时使用。

**两种模式**，由 `innodb_autoinc_lock_mode` 控制：

| mode | 行为 | 适用场景 |
|------|------|---------|
| 0 | 传统 auto-inc 锁，**语句结束**才释放 | 兼容老版本 |
| 1 | 普通 INSERT：申请后立即释放；`INSERT ... SELECT`：语句结束释放（默认） | 大多数场景 |
| 2 | 轻量级锁，申请后**立即释放** | 高并发插入 |

> [!warning] mode=2 + binlog=STATEMENT 会导致主从自增 ID 不一致
> 解决方案：将 `binlog_format` 设为 `ROW`，既保证并发性又避免数据不一致。

## 3. 行锁（重点）

### 3.1 Record Lock（记录锁）

锁定**单条索引记录**，阻止其他事务 UPDATE / DELETE 该行。

```sql
-- 对 id=1 的记录加独占锁
SELECT * FROM t WHERE id = 1 FOR UPDATE;
```

### 3.2 Gap Lock（间隙锁）

锁定**索引记录之间的间隙**，阻止其他事务在该间隙内 INSERT 新记录。**只在 RR 级别生效**。

```
索引记录:  [5] --- [10] --- [15] --- [20]

Gap Lock 作用于记录之前的间隙:
  (5, 10)  (10, 15)  (15, 20)  ← 这些是锁住的区间
```

> [!important] 间隙锁之间兼容
> 两个事务可以同时持有包含共同间隙的间隙锁，因为间隙锁的目标是**阻止插入**而非互斥访问。但一旦某个事务真的 INSERT 了记录落入该间隙，该记录上的 Record Lock 就会和其他事务的 Gap Lock 产生冲突。

### 3.3 Next-Key Lock（临键锁）★

**Record Lock + Gap Lock 的组合**，锁住左开右闭区间 `(prev_key, current_key]`。

```
对 age=10 加 next-key lock → 锁住 (5, 10]
  即间隙 (5,10) + 记录 10
```

#### 退化规则（核心）

加锁的基本单位是 next-key lock，但会根据**查询条件**和**索引类型**退化：

| 场景 | 退化结果 | 示例 |
|------|---------|------|
| 唯一索引 + 等值查询命中 | **Record Lock**（退化掉间隙锁） | `WHERE id=10`（id 是主键）→ 只锁 id=10 |
| 唯一索引 + 等值查询未命中 | **Gap Lock** | `WHERE id=13`（13 不存在）→ 锁 (10,15) |
| 非唯一索引 + 等值查询 | **Next-Key Lock → 对最后一个不满足条件的区间退化为 Gap Lock** | `WHERE name='Alice'`（name 有索引）→ 锁住所有 name='Alice' 的行，最后一个再包一个 Gap Lock |
| 范围查询 | **Next-Key Lock 链** | `WHERE id > 10 AND id < 20` → (5,10] (10,15] (15,20] |

#### 为什么能防止幻读

幻读的本质：同一事务内两次相同查询之间，其他事务 **INSERT** 了新行。

Next-Key Lock 的两道防线：

1. **Record Lock** 锁住已存在的行 → 防止 UPDATE / DELETE 导致数据变化
2. **Gap Lock** 锁住索引间隙 → 阻塞 INSERT，新行无法落入查询范围

```
事务A: SELECT * FROM t WHERE age BETWEEN 10 AND 20 FOR UPDATE;
  加锁区间: (5, 10] + (10, 15] + (15, 20] + (20, 25]
  等效锁住 [5, 25] 整个范围

事务B: INSERT INTO t (age) VALUES (12);
  → 阻塞！12 落入 (10, 15] 间隙，该间隙已被锁住
```

> 在 READ COMMITTED 隔离级别下，Gap Lock 被禁用，仅保留 Record Lock。这就是 RC 级别无法避免幻读的根因。

## 4. FOR UPDATE / FOR SHARE 详解

### 4.1 两种锁定读

| 语句 | 加锁类型 | 其他事务 |
|------|---------|---------|
| `SELECT ... FOR UPDATE` | 行级 **X 锁** | 不可 UPDATE / DELETE / SELECT ... FOR UPDATE；可普通 SELECT（快照读） |
| `SELECT ... FOR SHARE` | 行级 **S 锁** | 不可 UPDATE / DELETE；可 SELECT ... FOR SHARE；可普通 SELECT |

> MySQL 8.0 将 `LOCK IN SHARE MODE` 重命名为 `FOR SHARE`，旧语法仍然兼容。

### 4.2 不同隔离级别下的行为

| 隔离级别 | FOR UPDATE 加锁行为 | 防幻读？ |
|----------|---------------------|---------|
| READ UNCOMMITTED | 仅 Record Lock | 否 |
| READ COMMITTED | 仅 Record Lock（无 Gap Lock） | 否 |
| REPEATABLE READ（默认） | Next-Key Lock（Record + Gap） | **是** |
| SERIALIZABLE | 所有普通 SELECT 自动转为 `SELECT ... FOR SHARE` | 是 |

### 4.3 加锁范围示例

```sql
-- 假设表 t 有主键 id: 5, 10, 15, 20, 25

-- ① 唯一索引等值命中 → Record Lock
SELECT * FROM t WHERE id = 10 FOR UPDATE;
-- 锁: 只锁 id=10 这一行

-- ② 唯一索引等值未命中 → Gap Lock
SELECT * FROM t WHERE id = 13 FOR UPDATE;
-- 锁: (10, 15) 间隙，阻止插入 id=11~14

-- ③ 范围查询 → Next-Key Lock 链
SELECT * FROM t WHERE id >= 10 AND id < 20 FOR UPDATE;
-- 锁: (5, 10], (10, 15], (15, 20], (20, 25)
-- 即 id 在 [5, 25] 范围内的所有记录和间隙

-- ④ 非唯一索引等值查询
-- name 有普通索引，值: Alice(id=10), Alice(id=15), Bob(id=20)
SELECT * FROM t WHERE name = 'Alice' FOR UPDATE;
-- 锁: name 索引 (Alice, id=10) 和 (Alice, id=15) 两行 + 间隙锁
--    + 回表到主键索引锁 id=10 和 id=15
```

## 5. 死锁问题

### 5.1 死锁的四条件

Next-Key Lock 场景下全部满足：

| 条件 | 表现 |
|------|------|
| 互斥 | 行锁天然互斥 |
| 持有并等待 | 逐行加锁，持有已获得的锁去申请下一行 |
| 不可剥夺 | 事务提交前不释放锁 |
| 循环等待 | T1 等 T2 的锁，T2 等 T1 的锁 |

### 5.2 经典死锁场景

**场景一：反向加锁顺序**

```
-- 初始数据: id=1, 2, 3
T1: SELECT * FROM t WHERE id = 2 FOR UPDATE;  -- 锁 (1,2]
T2: SELECT * FROM t WHERE id = 3 FOR UPDATE;  -- 锁 (2,3]
T1: SELECT * FROM t WHERE id = 3 FOR UPDATE;  -- 等 T2 释放 ← 阻塞
T2: SELECT * FROM t WHERE id = 2 FOR UPDATE;  -- 等 T1 释放 ← 阻塞 → 💀 死锁
```

**场景二：二级索引 + 主键回表（加锁顺序不一致）**

```sql
-- name 是二级索引，id 是主键
-- T1 从 name 索引入手
T1: SELECT * FROM t WHERE name = 'Alice' FOR UPDATE;
    -- ① 在 name 索引上加 next-key lock
    -- ② 回表到主键索引，对 id 加 record lock

-- T2 从主键索引入手
T2: SELECT * FROM t WHERE id = 100 FOR UPDATE;
    -- 先拿主键 id=100 的锁

-- 互相等待对方持有的锁
T1: UPDATE t SET data = 'x' WHERE id = 100;    -- 等主键锁
T2: UPDATE t SET data = 'y' WHERE name = 'Alice'; -- 等二级索引锁 → 💀 死锁
```

**场景三：批量更新方向不一致**

```sql
-- 事务 T1 按 id ASC 扫描
T1: UPDATE t SET status = 1 WHERE status = 0 ORDER BY id LIMIT 100;

-- 事务 T2 按 id DESC 扫描 —— 同一批数据，反向遍历
T2: UPDATE t SET status = 1 WHERE status = 0 ORDER BY id DESC LIMIT 100;
-- 💀 高概率死锁
```

### 5.3 避免策略

| 策略 | 做法 | 优先级 |
|------|------|--------|
| **统一访问顺序** | 所有事务用相同的索引和排序方向 | 🔴 最重要 |
| **缩短持锁时间** | 把 RPC/HTTP/计算放到事务外 | 🔴 重要 |
| **减小锁粒度** | 分批 + `LIMIT` + `SKIP LOCKED` | 🟡 推荐 |
| **NOWAIT 快速失败** | `SELECT ... FOR UPDATE NOWAIT` — 不等待，上层重试 | 🟡 推荐 |
| **合理使用索引** | 无索引 → 全表扫描 → 全部锁住 | 🟡 基础要求 |
| **降低隔离级别** | `READ COMMITTED` 禁用 Gap Lock → 大幅降低死锁概率 | 🟢 权衡选择 |

#### SKIP LOCKED 示例

```sql
-- 跳过已被锁住的行，不等待，天然避免死锁
SELECT * FROM t WHERE status = 0
  LIMIT 100 FOR UPDATE SKIP LOCKED;
```

#### NOWAIT 示例

```sql
-- 遇到锁立即报错（不等待），应用层捕获并重试
SELECT * FROM t WHERE id = 100 FOR UPDATE NOWAIT;
```

### 5.4 排查方法

```sql
-- ① 查看当前锁等待链
SELECT
  r.trx_id              AS waiting_trx_id,
  r.trx_mysql_thread_id AS waiting_thread,
  b.trx_id              AS blocking_trx_id,
  b.trx_mysql_thread_id AS blocking_thread
FROM       information_schema.INNODB_LOCK_WAITS w
INNER JOIN information_schema.INNODB_TRX r ON r.trx_id = w.requesting_trx_id
INNER JOIN information_schema.INNODB_TRX b ON b.trx_id = w.blocking_trx_id;

-- ② 查看最近一次死锁日志（最重要！）
SHOW ENGINE INNODB STATUS\G
-- 找到 LATEST DETECTED DEADLOCK 段落

-- ③ MySQL 8.0+ 实时锁信息
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

### 5.5 应用层死锁重试

MySQL 检测到死锁时会自动回滚**代价较小**的事务，被回滚的一方收到 **Error 1213**。应用层做重试即可：

```go
import (
    "math/rand"
    "strings"
    "time"
)

func withDeadlockRetry(fn func() error, maxRetries int) error {
    for i := 0; i < maxRetries; i++ {
        err := fn()
        if err == nil {
            return nil
        }
        // MySQL Error 1213: Deadlock found when trying to get lock
        if strings.Contains(err.Error(), "Deadlock") ||
           strings.Contains(err.Error(), "1213") {
            // 随机退避，避免惊群
            time.Sleep(time.Duration(50+rand.Intn(100)) * time.Millisecond)
            continue
        }
        return err
    }
    return fmt.Errorf("max retries (%d) exceeded", maxRetries)
}
```

### 5.6 RR 级别特有死锁：Gap Lock + Insert Intention Lock

RR 级别下 Gap Lock 阻止插入，而 INSERT 需要申请 **Insert Intention Lock**（一种特殊的间隙锁）。两者冲突是 RR 特有的死锁根源。

#### 场景一：同间隙并发 INSERT

```sql
-- 前提：表 t 有唯一索引 idx_no，现有记录 no=10, no=20
-- 两个事务各自 SELECT 一个不存在的 no，获得 gap lock (10, 20)

T1: SELECT * FROM t WHERE no = 15 FOR SHARE;
    -- gap lock: (10, 20) ✓

T2: SELECT * FROM t WHERE no = 16 FOR SHARE;
    -- gap lock: (10, 20) ✓  （gap lock 之间兼容，两个事务都持有）

T1: INSERT INTO t (no) VALUES (15);
    -- 需要 Insert Intention Lock on (10, 20)
    -- 但 T2 持有该间隙的 gap lock → 阻塞，等 T2 释放

T2: INSERT INTO t (no) VALUES (16);
    -- 需要 Insert Intention Lock on (10, 20)
    -- 但 T1 持有该间隙的 gap lock → 阻塞，等 T1 释放
    -- 💀 死锁：互相等待对方释放 gap lock
```

#### 场景二：二级索引唯一性冲突引发间隙死锁

```sql
-- 二级索引 idx_name 的 B+ 树叶子: ['Alice',id=1] → ['Bob',id=3]
-- 两个事务同时 INSERT 同一个 name 值，落在同一个 gap

T1: INSERT INTO t (name, id) VALUES ('Amy', 100);
    -- 对 name 索引 gap ('Alice', 'Bob') 加 Insert Intention Lock

T2: INSERT INTO t (name, id) VALUES ('Amy', 101);
    -- 同一个 gap，也要 Insert Intention Lock

-- 若两条 INSERT 几乎同时到达，InnoDB 在检查唯一性时需要扫描 gap，
-- 双方各持有部分锁资源 → 💀 死锁
```

> [!tip] 根因
> RR 下 **gap lock 是先到先得**，多个事务可以同时持有同一个 gap 的共享 gap lock，但当各自尝试 INSERT 时，INSERT 需要的 Insert Intention Lock 和对方的 gap lock 冲突——形成循环等待。

#### RR 下防幻读锁导致的批量更新死锁

```sql
-- t 有索引 idx_status，现有 status=0 的行 id=10,20,30,40,50

T1: UPDATE t SET status = 1 WHERE status = 0 AND id >= 10 ORDER BY id LIMIT 3;
    -- 按 id 顺序加 next-key lock: (5,10], (10,20], (20,30]...
    -- 锁住 id=10,20,30 并提交释放

T2: UPDATE t SET status = 1 WHERE status = 0 AND id >= 10 ORDER BY id LIMIT 3;
    -- 同样顺序加锁: (5,10]...

-- 当两个事务交叉执行时：
T1 已锁 (5,10], (10,20]  正要锁 (20,30]
T2 已锁 (20,30]          正要锁 (10,20]
-- 💀 死锁：T1 等 T2 释放 (20,30]，T2 等 T1 释放 (10,20]
```

> 这在 RC 下**不会发生**，因为 RC 无 gap lock，id=20 被锁后 T2 只等 id=20 的 record lock，不会锁住 (20,30] 整个区间。

### 5.7 RC 级别下依然会遇到的死锁

RC 禁用了 gap lock，死锁概率大幅下降，但**不会降为零**。

#### 场景一：经典行锁交叉（RC/RR 均会发生）

```sql
T1: UPDATE t SET val = 1 WHERE id = 1;  -- 锁 id=1
T2: UPDATE t SET val = 1 WHERE id = 2;  -- 锁 id=2
T1: UPDATE t SET val = 1 WHERE id = 2;  -- 等 T2
T2: UPDATE t SET val = 1 WHERE id = 1;  -- 等 T1 → 💀 死锁
```

这是最基本的死锁，与隔离级别无关——只要两个事务**反向持有对方需要的行锁**就会发生。

#### 场景二：二级索引更新的加锁顺序差异

```sql
-- idx_status 是二级索引，id 是主键
-- idx_status 叶子节点按 (status, id) 排序

T1: UPDATE t SET status = 1 WHERE id = 10;
    -- ① 修改二级索引：先删旧 (0, 10) 的 record lock，再加新 (1, 10) 的 record lock
    -- ② 主键索引：锁 id=10

T2: UPDATE t SET status = 1 WHERE id = 20;
    -- ① 修改二级索引：删旧 (0, 20)，加新 (1, 20)
    -- ② 主键索引：锁 id=20

-- 当两个事务修改的二级索引记录相邻，且 UPDATE 执行计划
-- 先锁二级索引再锁主键时，如果交叉访问同一批索引页：
T1 已锁 idx(0,10)，要锁 idx(0,20) 所在页的某条记录
T2 已锁 idx(0,20)，要锁 idx(0,10) 所在页的某条记录
-- 💀 死锁（取决于索引页的物理布局）
```

> [!note] RC 的 `UPDATE` 在二级索引上仍然使用 **S lock** 做半一致性读
> RC 下 UPDATE 扫描到的每条记录先加 S lock 判断可见性，确认需要修改后再升级为 X lock。这个 S→X 的升级过程在多事务交叉时容易产生死锁。

#### 场景三：无索引导致全表锁

```sql
-- status 列无索引

T1: UPDATE t SET val = 'x' WHERE status = 0;
    -- 全表扫描，对每一行加 record lock（RC 下无 gap lock）

T2: UPDATE t SET val = 'y' WHERE status = 1;
    -- 同样全表扫描

-- 两个事务扫描顺序相反（InnoDB 按主键聚簇索引顺序扫描）
-- T1 正向扫描，T2 反向扫描 → 锁住同一批行但顺序相反
-- 💀 死锁
```

> 这是 RC 下最常见的死锁根因之一——**缺少合适的索引导致锁范围扩大**。

#### 场景四：INSERT + 二级索引唯一性检查

```sql
-- name 有唯一索引

T1: INSERT INTO t (name, id) VALUES ('Alice', 100);
    -- 检查 name 唯一性时，对 name='Alice' 的位置加 record lock（RC 无 gap lock）

T2: INSERT INTO t (name, id) VALUES ('Alice', 101);
    -- 同样检查唯一性

-- 若两个 INSERT 并发到达，都需要锁同一个位置来检查唯一性
-- 💀 死锁（即使在 RC 下，唯一索引的唯一性检查仍然需要加锁）
```

### 5.8 RC vs RR 死锁概率对比

| 维度 | RR | RC |
|------|----|-----|
| **Gap Lock** | ✅ 有 → 引入 Insert Intention 冲突 | ❌ 无 |
| **Next-Key Lock** | ✅ 有 → 锁范围更大 | ❌ 退化为 Record Lock |
| **死锁概率** | **较高**（gap lock 引入额外冲突维度） | **较低**（但不为零） |
| **主要死锁来源** | Gap Lock 交叉、INSERT 冲突、范围锁重叠 | 行锁交叉、二级索引加锁顺序、无索引全表锁 |
| **防幻读导致的死锁** | ✅ 范围查询的 next-key lock 链容易交叉 | ❌ 不防幻读，无此问题 |
| **适用策略** | 统一访问顺序 + 尽量缩小查询范围 | 加索引缩小锁范围 + 统一访问顺序 |

> [!tip] 选型建议
> 如果业务允许 RC 的幻读（大多数 OLTP 场景），用 RC 可以显著降低死锁概率。但 RC 下仍需保证：① 有合适的索引避免全表锁 ② 应用层有死锁重试逻辑。

## 6. 加锁规则速查

```
加锁基本单位: next-key lock（左开右闭）

等值查询:
  唯一索引命中        → Record Lock          (k, k]
  唯一索引未命中       → Gap Lock             (prev, next)
  非唯一索引命中       → Next-Key Lock 链     退化到 Gap Lock 收尾

范围查询:
  id >= 10 AND id < 20 → (5,10] (10,15] (15,20]   ← 全程 next-key lock 链
  id > 10 AND id <= 20 → (5,10] (10,15] (15,20] (20,25]

FOR UPDATE:  加 X 锁
FOR SHARE:   加 S 锁

RR 级别: Gap Lock 生效 → Next-Key Lock 防幻读
RC 级别: Gap Lock 禁用 → 仅 Record Lock → 不防幻读
```
