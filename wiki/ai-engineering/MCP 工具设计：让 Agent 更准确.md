# MCP 工具设计：让 Agent 更准确

> 来源：TRAE 官方知识库《如何让你的 Agent 更准确：MCP 工具设计技巧（上）（下）》。
> 本页是上下篇的合并摘要；原文保存在 `raw/2026/08/01/`，未修改。

## 核心命题

> 摘录：你不是在写 API，你是在教会一个智能体如何与这个世界交互。

MCP 工具不是 REST API 的机械封装，而是 Agent 的用户界面。LLM 看不到工具实现，只能通过三元组理解工具：

```text
工具 = 名称 + 描述 + 参数 Schema
```

因此工具设计的目标不是单纯暴露底层能力，而是降低 Agent 的认知负担：让它更容易判断“该用哪个工具、何时使用、参数怎么填、结果意味着什么、失败后如何修正”。

## 一、先理解调用链路

LLM 本身不执行函数。一次工具调用是应用程序与 LLM 之间的多轮协议：

1. 应用程序把工具定义和用户请求发送给 LLM。
2. LLM 根据名称、描述和 Schema 判断是否需要调用工具，并生成结构化调用请求。
3. 应用程序解析参数、执行真实函数，并处理权限、校验和副作用。
4. 应用程序把工具结果作为下一轮输入返回给 LLM。
5. LLM 生成最终回复，或继续调用工具。

MCP 的作用是标准化工具发现、Schema 暴露和调用转发，解决不同工具与不同 LLM 之间的 N×M 适配问题；它不改变 LLM tool calling 的基本机制。

一个重要边界是：工具 Schema 合法，不代表调用已经被授权。实际系统仍需要在执行侧做身份、权限、资源范围、风险等级和审计控制。这一点与企业 Agent 平台中的 Tool Registry/Policy 是互补关系，不应由 MCP 单独承担。

## 二、工具定义的六个设计维度

### 1. 命名：自解释、动词优先

工具名应让 Agent 不看实现也能快速判断用途：

- 用完整作用域、对象和动作：`github_create_issue`、`get_user_by_uuid`。
- 动词优先：`create`、`get`、`list`、`search`、`update`、`delete`、`send`、`run`。
- 用一致前缀形成语义分组，例如 `github_*`、`slack_*`、`calendar_*`。
- 不要使用 `get_user`、`delete_item`、`handler` 这类依赖上下文的模糊名称。
- 控制长度，把细节放进参数和描述；但具体长度上限取决于 MCP Client，应在目标 Client 上验证。

前缀还是后缀没有绝对答案，文章建议用实际评测选择一种，并在整个 Server 内保持一致。

### 2. 描述：写成可执行契约

工具描述至少回答四个问题：

- **What**：做什么？处理什么对象？
- **When**：什么时候应该使用？什么时候不要使用？
- **Constraints**：权限、前置条件、不可逆行为和输入限制是什么？
- **Output**：成功返回什么？失败可能是什么？

参数描述也要显式写出格式、示例、是否必填、默认值和边界。例如不要只写 `id`，而要写 `user_uuid`，并说明格式如 `usr_xxxxxxxx`。

当存在功能相近的工具时，在描述中明确选择顺序：标记一个工具为“推荐首选”，并说明底层/高级工具只有在什么条件下使用。

### 3. 输入：严格 Schema，宽容执行

输入设计目标是让 Agent 更容易传对、更难传错：

- 只把无法合理默认的参数设为必填。
- 为可选参数提供常用默认值，并在描述中写明默认值和最大值。
- 用 `enum` 限制离散选项，用 `pattern` 约束格式，用 `minimum/maximum` 约束范围。
- 复杂嵌套不要过深，尽量使用扁平 Schema；不同 LLM 对 JSON Schema 的支持不完全一致，必须在目标 Client/模型组合上测试。
- Schema 定义规范形式，但执行层可以兼容常见变体，并把输入归一化后再处理。
- 分页参数从 1 开始，返回 `total_count`、`has_next/has_more` 等明确元数据。
- 对复杂对象数组保持谨慎：文章建议在特定 LLM 不擅长稳定生成嵌套数组时，评估编号参数展开方案；这不是通用规则，应以评测结果决定。

文章还介绍了“静态确认参数”模式：对覆盖、删除、发送等高风险动作增加一个固定 enum 参数，要求模型在最后填入确认值，以重新触发安全提醒。该技巧只能作为辅助防线，不能替代用户确认、权限校验和服务端幂等/审计。

### 4. 输出：给 Agent 可操作的信息

输出应服务于 Agent 的下一步决策，而不是暴露底层实现：

- 结构化数据优先 JSON；面向用户阅读的长文本可用 Markdown；混合场景可用 JSON 包装摘要和结构化字段。
- 返回语义化字段和标准格式，减少无意义的 UUID、内部 epoch、过度具体的 MIME/尺寸字段。
- 成功结果包含足够上下文，例如状态、资源编号、标题、URL、时间和下一步可用字段。
- 大结果必须分页、过滤或截断；截断时返回 `truncated`、总量、已展示范围和下一步建议。
- 可通过 `response_format` 让调用方选择 concise/detailed，减少后续调用不需要的信息。
- stdio MCP Server 的正常通信不要向 stdout 打日志，日志写 stderr 或文件；具体实现应遵循所用 SDK 的通信约定。

### 5. 错误处理：错误是反馈，不是终点

对 Agent 来说，错误结果是下一轮规划的输入。错误信息应同时说明：

1. **What**：发生了什么错误。
2. **Why**：可能原因和期望格式。
3. **How**：如何修正，或应该改用哪个替代工具。

可恢复错误应返回重试、修正参数或等待时间；不可恢复错误应明确需要人工介入。复杂错误建议结构化返回：

```json
{
  "status": "error",
  "error_type": "VALIDATION_ERROR",
  "message": "Invalid email format",
  "suggestions": ["检查 @ 符号", "改用 find_user_by_id"],
  "recoverable": true,
  "requires_user_action": false
}
```

配置缺失也应在实际调用时给出诊断，而不是让 Server 在启动阶段无信息崩溃。错误消息不要泄露密钥等敏感信息。

### 6. 粒度：按使用场景聚合

两个极端都不好：

- 太细：Agent 需要多次调用、保存更多中间结果，浪费 token 和延迟。
- 太粗：一次返回大量无关信息，填满上下文并增加筛选负担。

更稳妥的原则是“按用户目标和常见工作流聚合，而不是按底层数据结构拆分”。如果 90% 的场景都是 A 后紧跟 B，可以考虑提供组合工具；同时保留底层工具处理需要精细控制的少数场景。

例如，把“查用户、查订单、查物流”编排成一次 `track_order(email)`，让编排逻辑留在代码中，而不是把中间状态和多次选择交给 LLM 上下文。

粒度选择取决于使用场景是否固定、用户是否需要逐步控制、Token 预算、错误处理方式和 Agent 的规划能力。

## 三、工具数量与 Server 边界

工具定义会持续占用 system prompt。工具越多，Token 成本、选择困难、注意力稀释和工具间混淆越明显。文章给出的经验建议是：单个 Server 控制在较小规模，摘要处提到 5-15 个；上篇还引用“20 个以内”的软性建议。它们都应视为待评测的经验阈值，而不是协议硬限制。

实践上：

- 一个 Server 聚焦一个领域或职责。
- 避免相似工具、版本残留和功能冗余。
- 定期统计从未调用、经常一起调用、经常失败和经常传错参数的工具。
- 未使用工具可以考虑删除或合并。
- 高权限管理能力可与普通用户能力分 Server，减少普通 Agent 的选择和风险暴露。
- 提供 `info/status` 诊断工具，返回版本、依赖状态、认证状态、配置检查和发现的问题，但不返回密钥本身。

## 四、可移植性：显式声明运行时与依赖

脚本和 MCP Server 不应依赖目标环境中隐式存在的解释器、全局包或固定路径。文章推荐：

- Python 使用 UV 和 PEP 723 内联依赖，`uv run script.py` 执行。
- Node.js 使用 `package.json` 配合 `npx`/`npm`。
- Bun 使用 `bun run` 或编译为独立文件。
- Deno 显式声明权限和依赖。
- Go/Rust 二进制便于单文件分发，但需要处理多平台构建和发布。

核心不是特定工具，而是“运行时、依赖和权限都显式声明”，确保本地、远程 Agent 和他人环境中的行为一致。

## 五、Skills 与 MCP：互补而非替代

MCP 适合高频、明确、需要强参数校验的 API 操作；Skills 适合低频但重要、需要丰富上下文和多步骤规程的工作流。

| 维度 | MCP | Skills |
|---|---|---|
| 定义 | 结构化 Schema | 自然语言指令 |
| 参数约束 | 强 | 依赖 Agent 理解 |
| 加载方式 | 通常会话内全量发现 | 元数据常驻，详情按需加载 |
| 适合 | 明确的工具调用 | 复杂工作流和最佳实践 |
| 主要风险 | 工具数量和 Schema 占用上下文 | 指令未被读取或理解不完整 |

组合方式是：Skill 描述何时使用、调用顺序、审查点和常见陷阱，MCP 工具负责实际执行。工具数量很大时，还可以用 MCPorter 把 MCP Server 转成 CLI，供 Skill 调用；但是否采用应考虑认证、连接复用、可审计性和运行环境。

## 六、落地检查清单

- [ ] 每个工具是否能仅凭名称、描述和 Schema 被正确理解？
- [ ] 名称是否动词优先、作用域明确、与同类工具风格一致？
- [ ] 描述是否写清 What/When/Constraints/Output？
- [ ] 参数是否只有必要的必填项，并写明示例、默认值、格式和范围？
- [ ] Schema 是否简单，且在目标模型和 Client 上实测过？
- [ ] 执行层是否做输入归一化、权限校验、幂等和副作用控制？
- [ ] 输出是否结构化、语义化、有限长，并带分页/截断信息？
- [ ] 错误是否包含原因、修正方式、替代工具和是否需要人工介入？
- [ ] stdio 通信是否避免 stdout 日志污染？
- [ ] 工具是否按用户目标聚合，而不是简单映射底层 API？
- [ ] Server 是否职责单一，工具是否存在重叠或长期未使用项？
- [ ] 运行时、依赖、配置和权限是否显式且可移植？
- [ ] 是否有离线评测验证工具选择、参数正确性、错误恢复和工具间混淆？

## 与现有 Agent 平台知识的连接

这篇文章解决的是“模型如何看懂和使用工具”的接口设计问题；现有企业 Agent 平台笔记进一步补充了“工具如何被注册、授权、观测和审计”。两者应串成一条链：

```text
Agent-friendly Tool Interface
  -> Tool Registry
  -> Policy / Permission
  -> Runtime / Workflow
  -> Trace / Evaluation
```

MCP 负责标准化接入，不等于完整的企业工具治理。好的工具描述降低模型决策错误；Registry、Policy、Runtime 和 Trace 则控制工具是否存在、能否调用、调用结果如何进入证据链，以及失败如何被评测和回收。
