# Agent 在企业固定流程中的嵌入边界

> Agent 与传统神经网络应用在原理上连续，都是把概率模型嵌入普通软件；差异在于模型是否进入运行时控制流。企业核心流程通常不应交给模型接管，Agent 的主要落点是固定流程中依赖人工处理的非结构化输入、模糊判断和长尾异常。

## 一、Agent 与传统神经网络应用的关系

两者都可以抽象为：业务程序向模型提供输入，模型完成不适合硬编码的判断，外围系统负责数据、状态和执行。因此 Agent 并未突破传统计算范式，也不具有脱离软件系统的自主性。

真正的工程差异在于模型承担的职责：

| 维度 | 传统神经网络应用 | LLM Agent |
|---|---|---|
| 典型任务 | 分类、检测、预测、排序 | 围绕目标推进多步任务 |
| 模型输出 | 标签、分数、特征 | 下一步动作、工具参数、结果解释 |
| 控制流 | 由代码预先定义 | 部分由模型在运行时决定 |
| 交互方式 | 通常单次推理 | 决策—行动—观察循环 |
| 错误形态 | 局部预测错误 | 可能沿工具调用链传播并产生副作用 |
| 主要约束 | 输入质量、模型指标、业务规则 | 还需权限、预算、终止、审批、审计和执行后验证 |

传统模型更像一个“智能函数”：程序询问风险分数，再按确定规则处理。Agent 则像受限的运行时控制器：在允许的动作集合中读取环境反馈并选择下一步。

> 传统 AI 应用是“程序调用模型做判断”；Agent 是“程序约束模型组织行动”。

## 二、企业流程固定，不等于所有节点都确定

企业核心流程被 IT 系统固化，是为了保证状态转换确定、权限明确、结果可审计、异常可补偿。账务计算、状态机流转、幂等判断、权限验证、清结算和定时调度等环节不应因为引入 Agent 而变成概率控制。

但完整业务并不只存在于流程图中。固定系统之间常有人工承担的“语义胶水”：

```text
固定系统 A
→ 人工阅读、收集、判断和改写
→ 固定系统 B
→ 人工查询制度、解释异常和选择分支
→ 固定系统 C
```

这些工作通常具有共同特征：目标和可选结果相对明确，但输入是自然语言、文档或跨系统记录，处理路径取决于中间结果，规则又难以穷举。企业不是没有开放性，而是将开放性压缩到了人工岗位和异常队列中。

因此，企业 Agent 不必寻找完全开放的目标任务，更实际的对象是：

> **目标明确、输出受限，但输入理解和中间判断具有不确定性的任务。**

## 三、固定流程中的四类嵌入点

### 1. 流程入口：非结构化输入转业务请求

将邮件、聊天记录、电话转录、合同、PDF 或图片转换成业务系统可接受的结构：识别意图、抽取字段、检查材料完整性，并指出仍需补充的信息。后续校验和状态流转仍由业务系统完成。

### 2. 流程中间：辅助模糊分类和判断

Agent 聚合多个页面、制度和历史记录，输出分类、依据、候选动作和置信度。典型场景包括工单路由、材料一致性检查、审批摘要、制度匹配和告警归因。初期应作为 Copilot，由人工确认后继续固定流程。

### 3. 异常分支：调查长尾问题

正常路径继续由规则自动处理；Agent 只调查系统状态不一致、外部接口非标准错误、材料与记录矛盾等长尾情况。它负责收集上下文、列出证据、归纳可能原因并推荐既有处理路径，无法判断时升级人工。

> Agent 更适合当异常处理的调查员，而不是业务状态的最终裁决者。

### 4. 流程出口：解释、总结和生成材料

业务系统完成处理后，Agent 根据权威事实生成客户解释、审批摘要、通知草稿和审计材料。模型只能组织表达，不得补全业务系统未提供的事实。

## 四、RAG、单次 LLM、Workflow 与 Agent 的边界

不要把所有使用大模型的系统都称为 Agent：

| 任务特征 | 优先方案 |
|---|---|
| 查知识、给出处、回答问题 | RAG |
| 摘要、抽取、分类、改写，单轮即可完成 | 单次 LLM 调用 |
| 输入和规则明确、分支可穷举、结果必须确定 | 普通代码或 Workflow |
| 稳定特征到标签/分数，且有足够样本 | 传统机器学习 |
| 跨多个信息源，下一步依赖上一步结果，路径难穷举 | Agent |

客服问答如果只需检索知识并回答，通常是 RAG；当任务还需要查询订单、核对支付和清算状态、判断建单条件，并在用户确认后提交工单时，才形成较完整的 Agent 闭环。

是否采用 Agent，可重点检查：

- 人工当前是否在执行“查询—判断—操作”的多步循环；
- 是否需要跨多个信息源或系统；
- 下一步是否依赖上一步返回结果；
- 是否包含大量自然语言或文档理解；
- 最终动作能否限制在明确集合中；
- 错误能否被检测、拒绝、回滚或转人工。

如果现有人工操作本身没有多步决策循环，通常也不需要 Agent。

## 五、推荐架构：工作流包住 Agent

```text
确定性工作流进入模糊节点
→ Agent 读取受限上下文
→ 输出结构化提案与证据
→ Schema、权限和业务规则校验
→ 自动执行 / 人工审批 / 降级处理
→ 业务服务执行状态转换
→ 查询最终状态并记录审计
```

关键边界是：

- 工作流拥有流程状态；
- 业务服务和数据库拥有权威事实；
- 权限系统决定允许做什么；
- Agent 只负责有限的语义判断和动作提案；
- 执行器负责真正修改状态；
- 审计系统记录输入、证据、建议、审批和最终动作。

> Agent 可以提议状态迁移，但不应绕过领域服务直接制造业务状态。

更完整的状态、权限、Context 和 Memory 设计见 [[业务 Agent 的受控执行与上下文治理]]。

## 六、自治应逐级开放

| 等级 | Agent 职责 | 执行权 |
|---|---|---|
| L0 | 检索、摘要、解释 | 无 |
| L1 | 分类、分析、提出建议 | 无 |
| L2 | 生成操作草稿或工具参数 | 人工确认 |
| L3 | 自动执行低风险、可逆、可验证操作 | 有限 |
| L4 | 在明确边界内完成多步任务 | 较高，但全程审计 |

合理演进顺序是先辅助找信息，再辅助判断，然后生成待确认操作，最后才对低风险动作开放有限执行权。每一级都应先积累真实失败样例和评测数据，再扩大权限。

## 七、核心结论

1. Agent 与传统神经网络应用在原理上没有断层，但模型从局部预测组件进入运行时控制流后，工程风险显著增加。
2. 企业核心业务流程固定是合理约束，不应为了使用 Agent 而主动开放化。
3. Agent 的主要价值不是接管流程，而是处理流程内原本由人工完成的非结构化理解、模糊判断、跨系统调查和结果解释。
4. 企业落地的基本形态应是“确定性工作流 + 概率性语义组件 + 受控工具调用”，而非给模型广泛权限后要求它自行办完。
5. 能用规则、SQL、状态机、传统模型或单次 LLM 调用解决的问题，不应包装成 Agent。
