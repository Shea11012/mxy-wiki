# 模型路由与工程化

> 模型路由不是按名字做 `if/else`，而是在能力、质量、延迟、成本、可用性、合规和数据边界之间做受约束决策，并能解释、回放和评测该决策。

## 一、请求闭环

```text
请求
 → 认证/租户/数据分类
 → 能力与上下文校验
 → 缓存资格判断
 → route policy
 → admission/rate limit/breaker
 → provider request（timeout + bounded retry）
 → validate/normalize
 → fallback 或返回
 → usage/cost/trace/eval feedback
```

计费、观测和审计应覆盖成功、失败、缓存、重试和 fallback，而不是只在最终响应时记录。

## 二、路由信号

### 硬约束

- 模态、tool calling、structured output、上下文窗口
- 数据驻留、provider allowlist、租户策略
- 模型/区域可用性和速率限制
- 最大费用、延迟 SLO、输出 token 需求

### 软目标

- 按任务类别预测的质量
- 首 token 和总延迟
- 输入/输出/缓存/推理 token 成本
- 历史错误率、限流和区域健康度
- prompt cache 命中机会

先过滤不满足硬约束的候选，再在剩余模型间优化软目标。路由日志要记录候选、被排除原因、最终选择和策略版本。

## 三、静态、学习型与级联路由

| 类型 | 做法 | 风险 |
|------|------|------|
| 规则路由 | task/tenant → 模型 | 易审计，但规则漂移 |
| 分类器路由 | 预测任务难度/类别 | 分类误差、训练分布漂移 |
| Bandit/在线学习 | 根据反馈探索利用 | 需要可靠 reward 和安全探索 |
| Cascade | 先小模型，不确定或失败再升级 | 双重成本、错误置信度 |
| Ensemble | 多模型生成/投票 | 成本高，相关错误不会被投票消除 |

必须与“固定单模型”基线比较净收益，避免路由器比节省的成本更贵。

## 四、超时、重试、熔断与降级

### 错误分类

- 可重试：连接中断、部分 5xx、429（遵守 `Retry-After`）
- 通常不可重试：认证、无效参数、权限/政策拒绝
- 未知副作用：工具或下游请求可能已成功，应先查询状态

重试应有最大次数、deadline、exponential backoff + jitter，并避免多层 SDK/网关同时重试造成放大。

### 熔断器

```text
Closed ──失败率/样本阈值──> Open
Open ──冷却──> Half-Open
Half-Open ──受限探测成功──> Closed
Half-Open ──失败──> Open
```

breaker 应按 provider/model/region/错误类型隔离，并设置最小样本量；业务 4xx 不应计入基础设施熔断。

### Fallback

Fallback 不是简单换模型：

- 能力是否兼容（工具、JSON、视觉、上下文）
- Prompt 与消息协议是否需转换
- 数据是否允许发往备用 provider
- 质量和成本是否仍符合策略
- 是否会重复有副作用的工具链

降级可以是更小模型、只读模式、缩短上下文、异步处理、缓存结果或明确返回不可用。

## 五、Token 与成本核算

`tiktoken` 只适用于它明确支持的 tokenizer/模型，不能作为所有 provider 的精确计数器。预估用于 admission 和预算；账单以 provider usage 与合同口径为准。

应分别记录：

- 输入、输出、reasoning、cache read/write token
- embedding、reranker、tool、存储和网络成本
- 重试与 fallback 的额外成本
- 按 run/session/task/tenant 归集的总成本

模型更新、chat template、tool schema 和图像输入都会改变 token 估算；差异告警要按 provider/model/version 分桶。

## 六、缓存

### 精确缓存

指纹至少包含：模型及版本、system/developer/user messages、tool schema、生成参数、响应格式、租户/权限域和知识版本。密钥、PII 与租户数据不能通过共享缓存泄漏。

### 语义缓存

仅 embedding 相似不够，应增加：

- task/domain/locale/tenant 过滤
- 时间敏感和个性化请求禁用
- tool/写操作禁用
- grounding source 与索引版本绑定
- 高风险场景关闭或二次验证
- TTL、删除传播和命中审计

相似度阈值必须用误命中成本驱动的 eval 校准，不能凭经验设置。

Provider prompt caching 与应用响应缓存不同：前者复用输入前缀计算，后者直接复用答案，风险和失效策略不能混用。

## 七、可观测性

建议 trace 结构：

```text
request
 ├─ policy/auth
 ├─ cache lookup
 ├─ route decision
 ├─ provider attempt 1
 │   ├─ request/stream
 │   └─ validation
 ├─ retry/fallback
 ├─ tool/retrieval spans
 └─ usage/billing/eval
```

关键指标：可用性、TTFT、端到端延迟、错误率、限流率、fallback 率、cache precision/hit rate、每成功任务成本、质量与安全回归。Prompt 和响应默认脱敏，日志有保留和访问策略。

## 八、安全

工具安全不能止于白名单、Schema 和审计，还需要：

1. 用户/服务身份与租户边界
2. 每个工具的 scoped capability 和资源范围
3. 参数语义策略（路径、域名、SQL、金额等）
4. 高风险调用审批或双重确认
5. 沙箱、网络 egress 和 secret broker
6. 工具结果视为不可信输入
7. 持久记忆、RAG、缓存和日志的注入/泄漏防护

## 九、模型发布

### 金丝雀与蓝绿

- **金丝雀**：逐步放量，适合在线观察质量、成本和错误；流量比例应分阶段且可自动回滚，不固定为 10%
- **蓝绿**：两套环境整体切换，适合基础设施与可快速回滚的发布；模型行为仍需代表性 shadow/canary 数据验证
- **Shadow**：复制生产请求到候选模型但不影响用户，适合离线比较；必须处理数据授权和额外成本

发布门禁应比较任务级成功、质量、安全、延迟和成本，并按语言、租户、任务类别分片，不能只看总体均值。

## 十、幻觉治理

原来的“事前 RAG → 事中 Citation 拒答 → 事后反馈”过于简化。更完整的防线：

- 明确任务是否需要事实性 grounding
- 选择权威、版本正确且有权限的来源
- 验证检索覆盖和上下文冲突
- 将引用绑定到 claim，并检查引用是否支持断言
- 对结构化事实使用确定性校验或业务规则
- 证据不足时澄清/拒答
- 对高风险输出实施人工审批
- 用线上反馈和事故回放更新 eval 集

RAG 和引用只能降低部分幻觉，不能保证答案正确。

## 十一、上线检查

1. 建立质量/延迟/成本/合规目标和单模型 baseline
2. 离线回放路由策略，再小流量 shadow/canary
3. 错误分类、deadline、单层有界重试和 breaker
4. 对 fallback 做能力与数据政策兼容检查
5. 缓存按租户、版本、权限和时效隔离
6. 记录策略版本、候选排除原因和任务级成本
7. 建立模型/Prompt/路由/缓存的联合回归集
8. 支持快速禁用 provider、模型、路由规则和语义缓存

> 路由系统优化的不是“单次调用最便宜”，而是满足质量与安全约束下的每个成功任务总成本。
