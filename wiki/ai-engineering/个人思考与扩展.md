# 个人思考与扩展

> 这一组材料的共同主题不是某个 Agent 框架，而是如何把模型能力变成可验证的软件工程流程：状态显式化、反馈前置、权限收窄、证据留存。

## 一、Memory：从“多存”转向“正确生命周期”

原始探索覆盖窗口、摘要、长期存储、衰减和多源检索。更完整的问题框架是：

```text
事件/对话
 → 候选提取
 → 来源、权限与敏感性校验
 → add/update/supersede/delete
 → 分类型存储
 → 任务触发的召回
 → 过滤、重排、预算注入
 → 使用效果评测
```

关键结论：

- token/对话/概念是粒度，不是记忆类型
- session start、per-turn、on-demand 是召回时机，可以组合
- 时间衰减只是排序信号；稳定偏好不应因“很久没提”自动失效
- 本地文件、全文索引、向量库和知识图谱不是成熟度阶梯，各自适合不同查询
- 记忆必须支持 provenance、冲突更新、过期、用户纠正和删除传播
- 记忆写入和召回都要做 Prompt injection 与租户边界测试

详见 [[Agent记忆系统]]。

## 二、AI Coding：计划不是目的，反馈才是控制面

### 2.1 推荐循环

```text
理解需求与风险
 → 只读探索代码和依赖
 → 复杂任务显式拆分
 → 影响分析
 → 小范围实现
 → 自动验证
 → 独立 diff/review
 → 人工审查高风险与产品体验
 → 记录决策和回归
```

### 2.2 对原工作流的纠正

- **Plan-first 不是所有任务的硬规则**：简单局部变更可直接执行；复杂、高风险、跨模块任务才需要显式计划。计划应持续更新，而不是一次生成后机械执行
- **“100K token/40% 后模型变笨”不是通用定律**：有效上下文受模型、任务、信息结构、工具输出和位置影响。应以任务回归和 context telemetry 决定清理/压缩阈值
- **Clear 不总优于 Compact**：clear 可恢复干净前缀，compaction 可保留长任务状态；两者要按证据保真、恢复成本和缓存权衡
- **TDD 很有效但不是唯一验证方式**：遗留代码、UI、迁移和探索任务可能需要 characterization test、property test、静态分析、视觉回归或人工 QA
- **子 Agent 审查不自动独立**：共享模型、Prompt、代码和错误先验会产生相关失败；关键变更仍需确定性工具和人审
- **AFK/夜班不是默认安全模式**：只有任务边界、沙箱、权限、预算、回滚和 grader 都明确时才适合无人值守

### 2.3 任务切片

垂直切片/Tracer Bullet 通常比按技术层水平切片更早得到端到端反馈，但数据库迁移、基础设施和安全基线有时必须先建立共享地基。切片原则应是：

- 每片有独立完成条件与验证方式
- 尽量减少共享写文件和隐藏依赖
- 先解决高不确定性与高风险假设
- 并行化只用于真正独立的任务
- 工件、接口和所有权清晰

### 2.4 人机分工

| 机器擅长 | 人应重点负责 |
|----------|--------------|
| 搜索、样板实现、批量修改、执行测试、diff 初审 | 需求取舍、架构边界、权限、不可逆操作、产品品味、最终责任 |

“人不逐行看任何内部实现”只适用于低风险、强契约、强测试的模块；安全、资金、数据迁移和公共 API 不能仅靠黑盒测试放行。

## 三、Agent Eval：评系统，不只评模型

Agent Eval 的对象应写成：

```text
Agent system = model(s) + prompt + tools + harness + memory + environment + policies
```

### 3.1 核心维度

| 维度 | 指标示例 |
|------|----------|
| Capability | 任务成功率、Pass@k、完成条件覆盖 |
| Reliability | 多次 rollout 方差、扰动鲁棒性、故障恢复 |
| Efficiency | token、工具调用、延迟、每成功任务成本 |
| Process | 轨迹合法性、无效循环、人工介入、状态一致性 |
| Safety | 权限越界、数据外泄、Prompt injection、错误副作用 |
| Calibration | 是否知道证据不足、是否正确追问/拒答 |

### 3.2 Environment-first

```text
Task → Agent ↔ Isolated Environment → State/Artifacts
                                     ↓
                                  Grader
```

- 可确定验证时优先单测、编译、状态差异和业务规则
- LLM judge 用于开放生成，并配 rubric、版本固定和人工校准
- grader、标准答案和秘密测试不得暴露给 Agent
- 动态环境应注入超时、乱序、工具失败、用户插话和权限变化
- 报 instance-level 结果、环境版本、重试和 harness 配置，不能只报 aggregate score

### 3.3 从 Eval 到发布

```text
离线回放
 → 回归集
 → 故障/安全测试
 → shadow
 → canary
 → 线上 outcome + trace
 → 失败聚类
 → 更新任务集
```

Eval 数据同样会过拟合。保留挑战集、持续加入真实失败，并把环境和 grader 版本化。

## 四、贯穿三个方向的原则

1. **单一事实源**：任务、记忆和工件避免多写入者和循环同步
2. **外部反馈优先**：测试、编译器、环境状态和权威来源胜过模型自评
3. **状态显式化**：计划、权限、预算、版本、完成条件和来源可审计
4. **最小权限**：自主程度越高，环境隔离、预算和人工接管越重要
5. **复杂度按收益引入**：先用单 Agent/简单检索 baseline，再证明 memory、sub-agent、router 或 tree search 的净收益
6. **模型能力不转移责任**：最终发布、数据和副作用责任仍属于系统设计者

## 五、后续实践清单

- 建一个带真实失败样例的 coding-agent eval 集
- 对同一任务比较单 Agent 与多 Agent 的成功率/成本
- 为长期记忆加入偏好变更、删除和注入测试
- 为 context compaction 做信息保真回归
- 为工具定义 side-effect class、审批和幂等策略
- 将线上事故自动归档为可复现 task + environment + grader

> AI 工程的竞争力不在于使用最多的 Agent 术语，而在于构建最短、最可信的“观察—行动—验证—恢复”闭环。
