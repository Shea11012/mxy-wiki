## 同步阻塞

文件读写默认采用这种操作模式。在这个模式下，当一个读写请求发出，调用者会等待执行者完成 IO 操作，在 IO 操作完成之前，调用者会被阻塞。一旦执行者完成，就会把最终的执行结果返回给调用者。

## 同步非阻塞

调用者的 IO 请求无论执行结果如何，都不会被阻塞。当没有数据就绪时，会立即返回 EAGAIN 的错误码，表明资源暂时不可用。当调用者接收到该错误码时，通常是稍后重试或者使用多路复用机制等待资源变得可用。

## 异步阻塞

更多的是存在于理论研究中，在实际应用场景很少遇到。因为阻塞通常发生在等待 IO 条件准备就绪或 IO 操作执行太慢时。异步的 IO 调用通常只是一个提交 IO 的过程，并不包含 IO 执行的过程，所以这里一般没有任何理由会阻塞。

## 异步非阻塞

是一种常见的异步 IO 编程模式。其处理流程通常分为 3 个核心步骤。
 - 调用者提交 IO 请求到队列中
 - 执行者异步处理 IO 操作
 - 执行者向调用者反馈结果（通过回调函数）
在这 3 个步骤中，通常是处理 IO 操作最耗时，提交 IO 的过程是很快的。一般把异步非阻塞 IO 简称为异步 IO。

在 Linux5.1 内核引入了 io_uring 机制，它在设计上是真正的异步，在提交 IO 时，只是把请求放到队列中，保证不会阻塞调用者。它不仅支持各种 IO 类型，包括文件和网络 IO，同时兼容缓冲 IO 和 Direct IO

# Linux 的 IO 模式实现

## 信号驱动

通过让内核在文件描述符的数据就绪时向应用程序发送信号，从而避免进程对 IO 持续等待。
原理是应用程序首先通过 sigaction 系统调用注册一个信号处理函数，并将其与文件描述符关联。当文件描述符的 IO 事件就绪时，内核向应用程序的进程发送一个信号，应用程序随后在信号处理函数中执行 IO 操作。
在实际应用中，信号驱动模式并不常见，主要是由于它的复杂性和多线程环境下的限制。信号可能会中断进程中非原子操作，引发竞态条件，特别是在大量 IO 发生时，信号处理可能造成显著的性能负担。因此通常会采用更高效的技术，如 IO 多路复用。

## 多路复用

是一种允许单个线程同时监控多个文件描述符，以检查它们是否可以执行 IO 操作的技术。一旦某个文件描述符处于就绪状态，通过多路复用相关调用就能迅速通知应用程序，使其可以立即执行相应的读写操作。尤其是在网络 IO 的文件描述符时尤为常见。

### select

开发者需要将一组文件描述符传递到 Linux 内核，内核负责判断这些文件描述符是否有读写事件。内核筛选出发生事件的文件描述符并且把它们标记出来，最后将这些信息复制回用户空间。开发者需要再次遍历这个集合找出可以进行读写的文件描述符。
这里发生了 2 次复制和 2 次循环：
- 从用户态复制集合到内核态，在从内核态返回集合到用户态
- 内核循环处理集合筛选哪些文件描述符有 IO 事件，用户态遍历找到有 IO 事件的文件描述符

select 的文件描述符集合大小被 FD_SETSIZE 定义，通常为 1024

select 因为频繁的内存复制，导致 CPU 和内存资源双重负担，造成资源浪费和性能降低，且需要通过多次轮询来检测文件描述符状态，且最多仅能处理 1024 个文件描述符，在处理大量文件描述符时效率较低。

### poll

本质上和 select 基本相同，都需要在用户态和内核态之间复制数据，并通过遍历的方式来处理和检测文件描述符。
poll 通过动态数组和内核中的链表机制突破了 select 的文件描述符限制，无论是 select 或 poll，都会因为频繁的数据遍历以及用户态和内核态之间的数据复制而产生性能负担。

### epoll

epoll 是一个有状态的调用，通过 epoll_create、epoll_ctl、epoll_wait 这 3 个操作，避免每次调用都需要传入所有的文件描述符集合。它使用了红黑树，提供了更快的查找速度。

epoll 维护了一个就绪事件链表，当文件描述符上有事件发生时，通过回调机制将事件添加到就绪链表，因此在 epoll_wait 调用时返回的全是有效事件，减少了不必要的操作。
