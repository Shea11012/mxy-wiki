# 上下文工程：Agent 上下文的布局、状态与压缩

> 本稿是《Clippings/上下文工程.md》的学习型源摘要，覆盖源文全部 H2/H3。外部论文、厂商文档和研究前沿只按源文的论述与限定呈现，不替代原始资料。

## 1. 总览：上下文决定什么

上下文是 Agent 在一次决策时实际看到的全部信息：系统指令、用户输入、历史 assistant 回复、工具定义、工具结果，以及环境观察和运行时状态。上下文工程是对这些信息进行选择、组织、注入、更新、压缩和隔离。

源文用 Coding Agent 说明最低工作背景：实时代码上下文、流程规范、环境信息。进入上下文的是对环境的观察、描述或配置，不是环境本身。组织文档化、公开决策、可检索记录会直接改善 Agent 的工作条件；因此这也是组织的信息管理问题。

ReAct 的形式化要点是：当前行动依赖截至当前的完整交互上下文，而不只是当前输入。模型 API 通常无状态，Harness 必须在每次调用时重建历史。完整历史最忠实但会增长；摘要、压缩和状态提炼必须保留影响下一步的决策、约束、失败和证据。

> **源文摘录**：上下文的质量才是 Agent 能力的真正关键

## 2. Agent 如何调用大模型：API 上下文结构

### 消息的四种角色

API 的 `messages` 有四种角色：`system` 承载开发者规则和约束，`user` 承载用户请求，`assistant` 承载模型文本或工具调用请求，`tool` 承载框架执行后的结果。工具定义不是消息角色，而是请求顶层的 `tools` 字段，包含名称、描述和参数 schema。四种角色加工具定义对应上下文的五类组成。

### 单轮对话：最简单的 API 调用

单轮调用通常是 `system -> user`，返回一条 `assistant` 文本。每次调用都是无状态的；需要的信息必须出现在本次请求中。该例子用于建立消息列表和返回消息的基本协议。

### 带工具调用的多轮交互：Agent 的核心循环

温哥华时间和天气的例子展示：模型可以在一次响应中提出两个无依赖的 `tool_calls`，Harness 并行执行，再将带 `tool_call_id` 的两个 `tool` 结果连同完整历史送回。若后一个工具参数依赖前一个结果，就要串行进入下一轮。模型负责提出调用请求，框架负责执行；工具结果回来后，模型决定结束或继续。

### 用代码实现 Agent 的核心循环

最小循环是：调用模型、追加 assistant、检查 `tool_calls`；有调用则执行并追加 tool，没调用则输出并停止。`messages` 逐轮增长。生产实现还需要最大迭代次数、参数解析和校验、错误处理、权限边界、取消机制及结果验证，防止重复调用和无限循环。

### 从 API 视角看上下文的构成

请求可视作稳定前缀与动态轨迹：`system + tools` 尽量稳定，`user + assistant + tool` 随交互增长，当前状态可在轨迹尾部追加。预算接近阈值时，批量压缩旧证据，同时保留决策、约束、失败和引用。该布局同时解释了 ReAct、缓存和压缩。

> **源文摘录**：“每次调用都是无状态的”

## 3. KV Cache 友好的上下文设计

### 从 API 消息到模型 Token：Chat Template

Chat Template 将结构化 API 消息转换为模型实际消费的线性 token 流，用特殊 token 标出角色和边界。不同模型家族模板不同，服务端通常自动转换。错误地把工具结果标作普通用户消息，可能破坏工具循环中的思维链保留；不同模型对历史 reasoning/thinking 的回传协议也不同，必须核对当前文档。模板还解释了为什么缓存对前缀的字节/token 稳定性敏感。

### KV Cache 的原理与约束

注意力用 Query 与历史 Key 匹配，再从 Value 汇总信息；KV Cache 保存已处理 token 的 K/V，避免每次重新投影历史。缓存按前缀匹配，首个不同 token 之后的状态需要重算，改动越靠前，重算范围通常越大。解码时新 token 仍需遍历历史缓存，所以长上下文仍受显存、带宽和线性注意力访问约束。

源文的三条工程结论是：稳定 system prompt 和工具定义；动态信息追加到末尾；使用标准 API 和 Chat Template，不要自行拼接纯文本角色。动态时间戳、用户配置、工具定义排序会破坏缓存。滑动窗口除了改变前缀，还会删掉关键工具结果，导致重复调用和循环。纯文本 `USER/ASSISTANT` 格式还会损害角色边界和工具协议理解。

### KV Cache 与 Prompt Cache：两个层级的缓存

KV Cache 是一次推理过程中的模型内部缓存；Prompt Cache 是跨 API 请求复用相同前缀计算结果的推理引擎/服务商优化。二者都利用前缀不变性，但层级不同；启用方式、计费、保留时间和命中边界依服务商而异。

### 缓存作为架构约束

缓存会反过来决定提示词布局：跨用户、跨会话可共享的稳定部分放在缓存边界前，用户和会话动态信息放在边界后。N 个二值运行时条件可能造成 `2^N` 种前缀变体。父子 Agent 若要共享 Prompt Cache，提示词、工具、模型、配置、消息前缀和思考配置需字节级对齐。工具结果被摘要替换时，替换字符串首次生成后应冻结，恢复会话也使用同一字节串。

### KV Cache 未必是一次性的：可编辑、可组合的“笔记”

源文将可编辑、可组合 KV Cache 作为研究前沿选读：prefill 可能把字段的语义结论写入下游 KV，字段自身 token 的直接贡献可能很小。带显式 CoT 时，局部字段修改可沿思考传播；没有 CoT 时，孤立修改可能被下游已烘焙结论掩盖。通过 RoPE 重定位，预计算的缓存块还可能组合到新位置。源文明确限定：这是研究阶段，生产默认仍应保持稳定前缀。

> **源文摘录**：“动态信息永远追加到末尾”

## 4. 提示工程：优化系统提示词

系统提示词是 Agent 的员工手册，应把身份、规则、流程、业务约束和完成条件写到可执行程度。好的检验是：聪明的新员工读完后知道下一步怎么做。

### 语气与风格：系统提示词的人格

明确输出长度、失败时的简洁方式和语气可改善一致性；大写的强限制只能留给真正关键的约束，过度强调会稀释优先级。

### 结构化提示：系统提示词的格式

XML 适合表达精确语义和边界，Markdown 适合人机共读的层次；有意义的标签名降低模型识别关系的负担。结构化不是装饰，而是帮助模型定位和区分信息。

### 流程驱动 vs 规则堆砌：系统提示词的组织方式

按验证、分类、预处理、执行、验证等 SOP 组织规则，比无优先级的规则堆更可靠。阶段、异常分支和完成条件使模型知道当前处境，也减少多条规则同时适用时的冲突。

### 业务规则细化：系统提示词的内容

产品规则必须由产品/运营明确，工程师负责忠实编码。源文用电话账单 Agent 的收费模式说明模糊规则的危险：谈判省钱可按提成，服务任务可固定收费，低成功率任务可预收不可退；退款和取消不得错误归类为“省钱”。成功率阈值、金额粒度、计费范围和例外都要写成可执行条件，避免模型自由裁量业务定义。

### Few-shot 示例：何时给模型看例子

当风格、格式、边界难以用规则描述时，少量高质量输入-输出示例比长篇抽象描述有效；模型已擅长且规则易写的任务不必加示例。示例可放系统提示或会话开头，但都应保持稳定；逐请求检索示例会改写前缀。两三个覆盖边界的示例通常优于大量重复示例。

### 工具定义的设计

工具定义应说明何时使用/禁止使用、参数意义和例子、性能建议、错误边界及与其他工具的协作顺序。工具 schema 通常属于静态前缀，但渐进式工具发现可只常驻名称和简述，模型搜索后把完整 schema 追加到轨迹末尾；追加不会改动此前 token，后续可继续复用。该模式依赖模型训练支持“工具定义出现在对话中间”，不是所有旧模型或自托管模型都适用。

### 提示注入：上下文安全的核心威胁

提示注入是外部网页、邮件、文档、PDF、图片元数据或记忆混入伪装指令，诱导 Agent 违背规则。工具 Agent 的风险更高，因为可能删除文件、发邮件或泄露数据。防御要区分指令与数据：给外部内容加来源标记，保持 `system/user/assistant/tool` 的角色结构，清洗常见攻击短语。它们只能降低风险，必须叠加最小权限、沙盒、高风险确认、独立审查和外发控制。Skill 和状态栏也可能成为更高信任的注入面。

> **源文摘录**：是 Agent 安全的核心威胁之一

## 5. 动态提示词与 Agent Skills

系统提示词越长，越浪费无关 token，也越稀释注意力。Skills 用渐进式披露把领域知识拆成可组合、可版本控制、按需加载的包。

### Skills：领域能力的可组合单元

三层结构：元数据层提供 `SKILL.md` 的 `name`/`description` 和路由条件；核心流程层按需加载完整指令；细则层再按需读取模板、参考资料和脚本。描述要短、像“何时使用/何时不使用”的路由条件，并可写反例来减少误触发。

### 如何编写一份可用的 Skill

Skill 应说明角色/读者、三到五条核心原则、正反例、禁止清单、合法例外、验证方式和参考资料。规则最好写成作用域、动作、例外、验证方式。写作 Skill 可从三到五篇范文开始，比较 before/after，把稳定规律写回；Skill 也可捆绑工具、模板和脚本。第三方 Skill 应像代码一样审查来源、指令、权限和附件。

### Skills 在上下文中的位置

规范主要规定加载顺序，不固定消息角色。Claude Code 可在调用处把正文作为 user 注入，Codex 可每轮渲染 catalog 为 developer 片段并把正文放入带 `<skill>` 的 user 片段；共同原则是少量目录常驻、完整正文按需加载。目录和正文首次进入都有成本，后续收益来自稳定前缀和只追加、不回写既有上下文。

### Skills 与工具的关系

Skill 加通用执行器可以避免把所有专用工具 schema 常驻系统提示；工具数量较小，领域流程按需进入上下文。工具发现和 Skill 载入共同体现渐进式披露，但工具权限和副作用仍需执行层治理，不能只靠描述或 Skill 指令。

> **源文摘录**：“不是把所有知识一次性塞给 Agent”

## 6. Agent 状态栏：通过元信息管理轨迹

### Agent 状态栏的理论基础

状态栏把任务进度、环境变化、工具计数和约束从分散轨迹提炼成末尾的结构化摘要。源文将上下文学习概括为更擅长检索而非自动归纳：模型能找原始记录，却不会稳定地替长轨迹建立索引或统计计数。状态栏因此把隐式状态变成可直接检索的知识，并借助末尾位置引导注意力。

状态栏可提升弱模型的准确率，强模型则主要节省思考 token、延迟和费用；但错误状态会被模型高度信任，准确率必须作为生产指标。能用代码确定性计算的状态应由代码维护；若不得不使用 LLM，应逐条抽取、再由代码汇总，不能让 LLM 一次性批量统计。状态栏是有损投影，不应在未验证覆盖范围前删除原始轨迹。

### Agent 状态栏的构成

信息类型包括：TODO/任务规划；事件时间、地点和间隔等侧信道；系统时间、工作目录、环境和异常提醒；工具调用计数；详细错误信息；操作系统、Shell 和 Python 版本。事件侧信道随事件追加，规划和环境状态随进展更新。组合使用会产生协同，例如计数器加错误信息促使 Agent 在重复失败后换策略。

### Agent 状态栏在上下文中的具体位置

API 层常将状态栏作为末尾 `user` 消息插入，使用 `<agent_status>` 标记。这里的 `user` 是协议槽位，不表示真实终端用户。放在末尾既靠近即将生成的 token，又不修改稳定 system 前缀。

### 状态更新的两种实现与缓存代价

每轮替换只保留最新状态：删除旧消息会使其后的短后缀失效，但不会重算更早前缀。持久追加完全保持只增不改，缓存友好，但陈旧状态累积并要求模型关注最新一条。状态大小 `S`、两次更新间新增后缀 `R`、更新次数 `N` 和缓存输入价格比例共同决定取舍；状态小、间隔长、会话受控时可追加，状态大或更新频繁时可替换。

## 7. 上下文压缩策略

### 为什么需要压缩：不只是长度问题

压缩有两种动机：防止窗口、成本和延迟失控；以及把散落原始材料变成更容易检索的高密度知识。上下文没满也可能因无关内容过多而腐化。

### 上下文学习的内部机制：检索而非推理

模型擅长查找某条记录，不擅长每次从大量记录重新统计。把“100 条记录中的计数”预先写成结构化结论，可将反复推理变成直接检索。上下文溢出是装不下，Context Rot 是装得下却找不到；压缩是主动提炼，不是期待模型从噪声中自动学习。Few-shot 的临时适配也属于会话内的快速适应，不等于参数训练。

### 压缩与 KV Cache：看似矛盾，实则互补

压缩发生在两次 API 调用之间。system 和工具定义不动；主要替换旧 tool 结果；替换点之后缓存失效，但替换前仍可复用。压缩是窗口失败与缓存重建之间的有意识权衡，应接近阈值批量触发，避免每轮扰动。

### 生产级的分层压缩机制

五层机制是：大工具输出落盘、上下文只留摘要预览；低价值噪声直接删除；必要时使用 API 层微压缩；逐轮做归档式结构摘要；最后才做 LLM 全量压缩，并对连续失败设置熔断器。大输出的替换字符串应冻结，以维持会话恢复后的字节一致。

### 压缩策略的设计原则

信息价值不均匀，应优先决策、约束、验证和失败路径；保留语义完整性，不能把带时间和组织的事实压成无主体的短句；按任务调整保留面，检索重广度、分析重深度、创作重启发；压缩本身需要深层理解，最好可审查、可回溯。源文建议优先级：架构决策/关键约束，修改文件/变更，验证 pass/fail，未解决 TODO/回滚笔记，最后才是可删减的工具原文。

### 隔离优于压缩：子 Agent 上下文隔离

搜索或深度研究子 Agent 在独立上下文处理海量中间材料，只把结论和引用返回主 Agent。这样从源头阻止噪声进入主轨迹，也避免事后有损压缩和额外调用；代价是子 Agent 看不到父上下文，任务描述必须自包含、目标明确、输出带必要证据。它适合大范围搜索、检索和中间推理。

> **源文摘录**：隔离则让噪声从一开始就与主上下文绝缘

## 8. 实验记录

- **实验 2-1：本地 LLM 服务部署与工具调用。** 以 0.6B 级本地模型观察提示设计、100 token/s 以上的示例性能、ReAct、多轮工具调用、流式输出和 KV Cache 首 token 延迟。保持 system 前缀不变与修改前缀的对照用于观察缓存命中差异；还观察 `<think>`、工具参数生成、并行调用和终止判断。
- **实验 2-2：注意力机制可视化。** 用“北京的天气怎么样”说明 Query/Key/Value；观察因果三角形、注意力 Sink、思考/输出的回看模式和开头/结尾位置偏好。实验用于理解 KV Cache 和上下文学习依赖，而非把单张热力图当作普遍定律。
- **实验 2-3：常见的错误上下文管理模式。** 对照动态 system、动态用户配置、工具动态排序、滑动窗口和纯文本格式化。结论是动态内容应后置、工具顺序应稳定、完整工具证据不能随意滑出，标准角色格式不能被字符串拼接替代。
- **实验 2-4：提示工程消融实验。** Tau-Bench 航空和零售任务中，语气变化对完成率影响有限；打乱规则层次使成功率下降超过 30%；删除工具描述使工具调用错误率增加 45%。源文把信息组织和工具说明视为高影响因素，数值仍应在自身基准复测。
- **实验 2-5：提示注入攻防实验。** 测试直接注入、网页隐藏文本的间接注入、跨会话记忆注入；比较无防御、系统警告、外部来源 XML 标记和组合防御，并记录各类攻击成功率。
- **实验 2-6：从论文生成演示文稿。** 通过 PPTX Skill 的目录识别、正文加载、细则读取、模板和脚本调用，从 PDF 生成 10-15 页演示文稿。验收包括覆盖主要内容、至少三张一致图表和可打开的文件。
- **实验 2-7：从个人范文创建写作 Skill。** 用三至五篇原创范文生成初版 Skill，在新题目上比较 before/after 并回写稳定规则。验收关注触发条件、三至五条带示例的原则、作用域和例外。
- **实验 2-8：注意力可视化验证状态栏。** 对比无状态栏与末尾状态栏：前者从三次电话记录中重新计数，后者直接使用 `3/3` 约束。源文进一步报告上下文蒸馏基准：弱模型获得准确率，强模型获得效率；状态栏错误会原样传递。
- **实验 2-9：状态栏技术。** 实现时间戳、工具调用计数器、TODO、四层错误信息和系统状态感知。源文示例报告 TODO 可减少迭代和遗漏，详细错误信息可提升替代方案成功率；组合使用会产生时序、成本感知和自适应策略的协同。
- **实验 2-10：上下文压缩策略对比。** 比较无压缩、个体摘要、组合摘要、上下文感知压缩、带引用压缩、自适应窗口化。源文报告无压缩会在 128K 预算下溢出；上下文感知压缩按查询和阶段保留事实；自适应策略约 80% 阈值触发、批量压缩并用 `[COMPRESSED]` 防重复。压缩率和 token 数是该实验设置的结果，不应脱离任务复用。

## 9. 思考题主题

1. 在滑动窗口与完整历史之间设计保留关键证据、控制长度且保持稳定前缀的策略。
2. 比较 Qwen3 历史 thinking 保留、DeepSeek R1 剥离和 DeepSeek V4 强制回传，思考超长 ReAct 循环的协议设计。
3. 评估极端上下文感知压缩的不可逆损失，设计引用、分层摘要和回溯机制。
4. 处理状态栏计数错误、信任过高和状态投毒，建立确定性维护、校验和审计。
5. 防止多人维护系统提示词造成层次和规则的“熵增”，考虑版本控制、评测、审查和结构化模板。
6. 若上下文学习偏向检索而非推理，探索蒸馏、索引、外部记忆、程序化状态和更强的推理机制。
7. 解决 Skill 触发的元认知问题：边界描述、反例、路由评测、主动发现和人工兜底。
8. 评估不同模型对动态 Skill 指令、消息角色、历史思维链和工具定义位置的支持差异。
9. 在工具集频繁变化的系统中，把稳定目录、延迟加载、固定排序和动态尾部注入组合起来最大化缓存命中。

## 10. 本章主线

API 消息结构定义骨架；稳定前缀服务缓存；系统提示词承载规则；工具定义承载外部能力；Skills 按需承载领域知识；状态栏把运行时隐式状态显式化；压缩提高历史信息密度；子 Agent 隔离把中间噪声挡在主上下文之外。所有机制都受同一边界约束：要让模型在当前决策点看到足够、可信、结构清楚且成本可控的信息。
