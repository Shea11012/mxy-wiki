# DTM 缓存一致性方案

DTM 开源项目（dtm-labs/dtm + dtm-labs/rockscache）提出的缓存一致性解决方案。
通过**标记删除**（TagDeleted）+ **二阶段消息**保证 Redis 缓存与数据库的最终一致性。

## 问题根源

> 摘录：由于服务1发生了进程暂停（例如由于GC导致），因此当它往缓存当中写入v1时，覆盖了缓存中的v2，导致了最终的不一致

并发操作与进程暂停（如 GC）可能导致缓存被旧数据覆盖。分布式锁也无法彻底解决——DDIA 作者 Martin Kleppmann 对此有专门讨论。

## 传统方案缺陷

| 方案 | 做法 | 问题 |
|---|---|---|
| 短过期时间 | 以不一致窗口换 DB 高负载 | 窗口内不一致，DB 压力大 |
| 延时双删 | 删缓存→更新DB→sleep→再删缓存 | 只降低概率，无法保证；sleep 时间难定 |
| 应用层版本机制 | 应用层做版本校验 | 侵入性强，难以复用 |
| 分布式锁 | 加锁防并发 | 无法解决 GC 暂停导致的覆盖问题 |

## 标记删除机制

### 缓存数据结构

每个缓存条目是一个 hash，包含：
- **value** — 数据本身
- **lockUntil** — 锁到期时间
- **owner** — 锁持有者 UUID

### Fetch 函数（查询逻辑）

> [!warning] INFERRED — 以下为推理结论
> Fetch 查询逻辑：缓存为空且被锁定则睡眠等待；为空且未锁定则同步取数据；有数据则立即返回并异步取数据。
> 源文锚点：raw/2026/05/31/dtm缓存一致性.md 第 58-62 行

"取数据"内部流程：
1. 判断是否需更新（数据为空未锁定，**或**锁已过期）
2. 若需更新 → 锁定缓存 → 查询DB → 校验锁持有者无变化 → 写入缓存 → 解锁

### TagDeleted 函数（更新逻辑）

> 摘录：当DB数据更新时，通过dtm确保数据更新成功时，将缓存"标记删除"（保证原子操作的原理，后面一节展开详细讲解）；标记删除会将数据过期时间设定为10s，将锁设置为已过期，触发下一次查询缓存时的"取数据"

**原子性保证**：通过 DTM 的二阶段消息事务保证。代码示例：

```go
msg := dtmcli.NewMsg(DtmServer, gid).
    Add(busi.Busi+"/DeleteRedis", &Req{Key: key1})
err := msg.DoAndSubmitDB(busi.Busi+"/QueryPrepared", db, func(tx *sql.Tx) error {
    // update db data with key1
})
```

> 摘录：这段代码，DoAndSubmitDB会进行本地数据库操作，进行数据库的数据修改，修改完成后，会提交一个二阶段消息事务，消息事务将会异步调用 DeleteRedis。假如本地事务执行之后，就立刻发生了进程 crash 事件，那么 dtm 会进行回查调用 QueryPrepared

### 正确性证明

> 摘录：假如最后写入数据库的版本为Vi，最后写入到缓存的版本为V，写入V的uuid为uuidv，那么一定存在以下事件序列：数据库写入Vi -> 缓存数据被标记为删除 -> 某个查询锁定数据并写入uuidv -> 查询数据库结果V -> 缓存中的锁定者为uuidv，写入结果V

V 的读取发生在写入 Vi 之后，所以 V = Vi，保证最终一致性。

## 防击穿特性

标记删除法综合了「更新缓存」和「删除缓存」的优势：

| 场景 | 更新缓存的问题 | 删除缓存的问题 | 标记删除的表现 |
|---|---|---|---|
| 冷数据 | 浪费内存和计算 | 无问题 | 与删除策略一致，多保留 10s |
| 热点+快计算 | 乱序不一致概率高 | 击穿风险 | 5~8ms 返回过期数据，差别不大 |
| 热点+慢计算(3s) | 同上 | 大量请求 3s 阻塞 | 3s 内返回旧数据，优于阻塞 |
| 低频数据 | 浪费 | 无问题 | 与删除策略一致 |

> [!note] 极端情况
> 原先缓存中没有数据，突然大量请求到来——这对所有方案都不友好，需要通过预热解决。标记删除法已将打到 DB 的请求量降到最低，表现不弱于任何方案。

rockscache 内置防护：
- **防穿透**：`EmptyExpire` 缓存空结果（设为 0 关闭）
- **防雪崩**：`RandomExpireAdjustment` 随机偏移过期时间

## 从库延时处理

主从分离架构下，缓存删除后从库可能还未同步，查询从库拿到旧数据。两种方案：

1. **区分一致性要求**：高一致性数据强制从主库读取。rockscache 将并发请求拦截在 Redis 层，每个数据最多一个请求到 DB，主库读取可行
2. **监听末端从库 binlog**：主从采用不分叉的单链架构，监听最末端从库的 binlog 来触发标记删除

## DB 与缓存操作的原子性（4 种方案）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 短缓存时间 | 过期时间设短，如 1 分钟 | 简单 | 不一致窗口长，DB 负载高 |
| 消息队列 | 写本地表→轮询→MQ→消费更新缓存 | 可靠 | 架构重，维护成本高 |
| 订阅 binlog | canal 监听 binlog 同步缓存 | 可靠 | 架构重，资源浪费 |
| **DTM 二阶段消息** | `DoAndSubmitDB` + 回查 | **简单、轻量、易维护** | 依赖 DTM |

## 强一致性模式

前提：**所有数据读取都必须通过缓存**。

> [!important] 应用层强一致 ≠ 系统层强一致
> 两个独立系统之间不可能做到"同时更新"——理论上有时间间隔就一定不一致。但应用层强一致可以做到：要求所有数据读取只从缓存获取，不同时从缓存和 DB 混合读取。

### 写入策略

先更新 DB，再更新缓存（支持降级）。写入 DB 成功但缓存更新失败时：
- 应用**不立即返回成功**，等缓存也更新成功后再返回
- 用户看到「处理中」→ 符合强一致；看到「成功」→ 缓存已更新 → 所有读取都是最新数据

### 读取策略

打开 `StrongConsistency` 选项后，`Fetch` 不再返回旧数据，同步等待最新结果。
代价：增加延迟 + sleep 等待消耗资源。

## 方案对比总结

| 场景 | 推荐方案 |
|---|---|
| 最简单 | 设定较短缓存时间，允许少量不一致 |
| 保证最终一致+防击穿 | DTM 二阶段消息 + rockscache 标记删除 |
| 强一致 | DTM 二阶段消息 + rockscache 强一致模式 |
| 严苛强一致（含升降级） | DTM 二阶段消息 + rockscache 强一致 + 升降级兼容 |
