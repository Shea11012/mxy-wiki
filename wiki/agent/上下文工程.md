# 上下文工程

## 1. 什么是上下文工程

> 摘录：在推理阶段，如何策划与维护"最优的信息集合（tokens）"

上下文工程（Context Engineering）是提示工程的自然演进。提示工程关注"如何写出有效提示"，而上下文工程关注的是**在每一次模型调用前，如何以可复用、可度量、可演进的方式，拼装并优化输入上下文**。其核心工具 ContextBuilder 需要依赖 [[Agent记忆系统设计|记忆系统]] 和 [[RAG检索增强生成|RAG 检索]] 作为信息来源，三者协同构成 Agent 的完整上下文管理方案。

上下文 = LLM 采样时包含的那组 tokens。工程问题 = 在 LLM 的固有约束下，优化这些 tokens 的效用。

## 2. 为什么上下文工程重要

### 2.1 上下文腐蚀（Context Rot）

> 摘录：随着上下文窗口中的 tokens 增加，模型从上下文中准确回忆信息的能力反而下降

针堆找针(needle-in-a-haystack)基准揭示了这一现象。根源在于 Transformer 架构：每个 token 与上下文中所有 token 建立 n² 级别的两两注意力关系，随着上下文增长，建模能力被"拉薄"。

> 摘录：上下文必须被视作一种有限资源，且具有边际收益递减

位置编码插值等技术可以让模型适配更长序列，但会牺牲位置精确理解。这是**性能梯度**而非悬崖式崩溃：长上下文依旧强大，但精度有所下降。

### 2.2 有效上下文的解剖学

> 摘录：用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率

| 组件 | 要求 | 常见误区 |
|---|---|---|
| **系统提示** | 分区组织(Role/Task/Tool指引/Output)，最小必要信息集 | 过度硬编码(if-else) / 过于空泛(缺具体信号) |
| **工具** | 职责单一、接口清晰、token 友好、对错误鲁棒 | 臃肿工具集导致选哪个工具的决策含混 |
| **示例** | 精挑多样典型示例，胜过千言万语 | 把所有边界条件罗列塞进提示 |

### 2.3 JIT 上下文与智能体式搜索

> 摘录：后者不再预先加载所有相关数据，而是维护 **轻量化引用** （文件路径、存储查询、URL 等），在运行时通过工具动态加载所需数据

传统方式是推理前一次性检索（embedding），新方式是**及时（Just-in-time）上下文**。引用的元数据本身也帮助精化行为：目录层级、命名约定、时间戳隐含传达目的与时效。

渐进式披露（progressive disclosure）：每步交互产生新上下文，反过来指导下一步决策——文件大小暗示复杂度、命名暗示用途、时间戳暗示相关性。

**混合策略**更有效：前置加载少量高价值上下文保证速度，然后允许智能体按需自主探索。

### 2.4 长时程任务的三大策略

| 策略 | 适用场景 | 核心机制 | 经验法则 |
|---|---|---|---|
| **压缩整合** | 长对话连续性 | 接近上限时高保真总结，用摘要重启新窗口 | 先优化召回（不遗漏），再优化精确度（剔冗余） |
| **结构化笔记** | 里程碑/阶段性成果 | 关键信息写入上下文外的持久存储（TODO/NOTES.md） | 以极低上下文开销维持持久状态 |
| **子代理架构** | 复杂研究/分析 | 主代理规划，子代理在干净窗口中深挖，回传 1000-2000 token 摘要 | 关注点分离，庞杂搜索留在子代理内部 |

## 3. ContextBuilder：GSSC 流水线

### 3.1 设计目标

> 摘录：将"获取(Gather)- 选择(Select)- 结构化(Structure)- 压缩(Compress)"抽象为可复用流水线

四个核心目标：
- **统一入口**：减少 Agent 实现中的重复模板代码
- **稳定形态**：固定骨架模板（Role & Policies / Task / State / Evidence / Context / Output），便于调试和 A/B 测试
- **预算守护**：token 预算内保留高价值信息，超限兜底压缩
- **最小规则**：不引入来源/优先级等分类维度，用相关性+新近性简单评分

### 3.2 核心数据结构

**ContextPacket**（候选信息包）：
- `content: str` — 信息内容
- `timestamp: datetime` — 时间戳
- `token_count: int` — Token 数量
- `relevance_score: float` — 相关性分数 0.0-1.0
- `metadata: dict` — 可选元数据

**ContextConfig**（配置）：
- `max_tokens: int = 3000` — 最大 token 数
- `reserve_ratio: float = 0.2` — 系统指令预留比例
- `min_relevance: float = 0.1` — 最低相关性阈值
- `recency_weight: float = 0.3` — 新近性权重
- `relevance_weight: float = 0.7` — 相关性权重（两者之和 = 1.0）

### 3.3 四阶段详解

**Gather（多源信息汇集）**：从系统指令(relevance=1.0,不参与评分)、[[Agent记忆系统设计|记忆系统]]、[[RAG检索增强生成|RAG 系统]]、对话历史(最近5条)、自定义包五个来源汇集。每个外部数据源调用用 try-except 包裹，单源失败不影响整体。

**Select（智能信息选择）**：
1. 分离系统指令（relevance=1.0）和其他信息
2. 综合分数 = `relevance_weight × 相关性 + recency_weight × 新近性`
3. 过滤低于 `min_relevance` 的信息
4. 贪心选择：按分数从高到低填充直到 token 上限

相关性计算：Jaccard 相似度（关键词重叠，生产环境可替换为向量相似度）。新近性计算：指数衰减模型，24 小时内保持高分，衰减系数 0.1。

**Structure（结构化输出）**：将选中信息组织为分区模板 `[Role & Policies] → [Task] → [Evidence] → [Context] → [Output]`

**Compress（兜底压缩）**：按双换行分段，逐段检查 token 数，完整保留或截断并标注 `[... 内容已压缩 ...]`。token 估算：中文 1 字符 ≈ 1 token，英文 1 单词 ≈ 1.3 tokens。

### 3.4 与 Agent 集成

完整实现详见 [[raw/2026/06/10/第九章 上下文工程#9.3.4 完整使用示例|源文]]（`ContextAwareAgent` 类定义及使用示例）。

### 3.5 最佳实践

1. 根据任务复杂度动态调整 `max_tokens`
2. 生产环境用向量相似度替代关键词重叠
3. 不变的系统指令和知识库内容做缓存
4. 记录每次构建的统计信息（选中数量、token 使用率）
5. 关键参数（相关性权重、新近性权重）通过 A/B 测试找最优

## 4. NoteTool：结构化笔记

### 4.1 定位

> 摘录：NoteTool 是为"长时程任务"提供的结构化外部记忆组件。它以 Markdown 文件作为载体，头部使用 YAML 前置元数据记录关键信息

NoteTool 填补 [[Agent记忆系统设计|MemoryTool]] 的 gap：MemoryTool 关注对话式记忆（短期/情景/语义），NoteTool 关注**项目式任务**的结构化管理。

### 4.2 存储格式

每个笔记是独立 `.md` 文件，YAML frontmatter + Markdown 正文（详见 [[raw/2026/06/10/第九章 上下文工程#9.4.2 存储格式详解|源文]]）。

维护 `notes_index.json` 索引文件用于快速检索。

### 4.3 七个核心操作

| 操作 | 功能 | 关键参数 |
|---|---|---|
| `create` | 创建笔记，生成唯一 ID，更新索引 | title, content, note_type, tags |
| `read` | 读取笔记，解析 YAML+Markdown | note_id |
| `update` | 更新字段和内容，刷新时间戳 | note_id, title/content/tags 可选 |
| `search` | 关键词搜索标题和正文 | query, limit, note_type, tags |
| `list` | 列出笔记，按更新时间倒序 | note_type, tags, limit |
| `summary` | 统计：总数、类型分布、最近5条 | — |
| `delete` | 删除文件和索引条目 | note_id |

### 4.4 笔记类型优先级

| 类型 | 用途 | 优先级 |
|---|---|---|
| `blocker` | 阻塞问题 | 最高 |
| `action` | 下一步计划 | 高 |
| `task_state` | 阶段性进展 | 中 |
| `conclusion` | 重要结论 | 中 |
| `reference` | 参考资料 | 低 |
| `general` | 通用 | 默认 |

### 4.5 与 ContextBuilder 集成

检索相关笔记 → 转为 ContextPacket（按笔记类型设不同 relevance）→ 注入上下文：

笔记类型到 relevance 的映射详见 [[raw/2026/06/10/第九章 上下文工程#9.6.3 核心实现|源文]]（`blocker: 0.9, action: 0.8, task_state: 0.75, conclusion: 0.7`）。ContextBuilder 在 `build()` 时将 note_packets 和其他来源一起参与 Select 阶段评分。

## 5. TerminalTool：即时文件系统访问

### 5.1 设计理念

> 摘录：智能体不需要预先加载所有文件，而是按需探索和检索

实现 JIT 上下文理念。典型场景：代码库探索（find/grep/head）、日志分析（tail/grep/cut/sort/uniq）、数据预览（head/wc）。

### 5.2 四层安全机制

| 层级 | 机制 | 说明 |
|---|---|---|
| 第一层 | 命令白名单 | 只允许 ls/cat/head/tail/find/grep/wc/sort/cut/awk/sed/pwd/du/df 等只读命令 |
| 第二层 | 工作目录沙箱 | 只能访问指定 workspace 及子目录，禁止 `..` 逃逸 |
| 第三层 | 超时控制 | 每个命令有执行时间限制（默认 30 秒） |
| 第四层 | 输出大小限制 | 防止内存溢出（默认 10MB 截断） |

### 5.3 核心功能

**命令执行**：`subprocess.run` 在 `cwd` 下执行，合并 stdout/stderr，检查返回码，捕获超时和异常。

**目录导航**：`cd` 命令特殊处理，支持 `..`/`.`/`~`/相对路径，每次切换前检查是否在 workspace 内。

### 5.4 典型使用模式

探索式导航详见 [[raw/2026/06/10/第九章 上下文工程#9.5.2 核心功能详解|源文]]（逐步探索代码库）；日志分析详见 [[raw/2026/06/10/第九章 上下文工程#9.5.2 核心功能详解|源文]]；代码库分析详见 [[raw/2026/06/10/第九章 上下文工程#9.5.3 典型使用模式|源文]]。

### 5.5 与其他工具协同

- **+MemoryTool**：TerminalTool 发现的项目结构存入语义记忆
- **+NoteTool**：发现的性能瓶颈记录为 blocker 笔记
- **+ContextBuilder**：代码结构和 git 历史转为 ContextPacket 注入上下文

## 6. 实战：代码库维护助手

### 6.1 三层架构

| 层 | 组件 | 职责 |
|---|---|---|
| 即时访问层 | TerminalTool | 按需探索代码库，不预先索引 |
| 会话管理层 | ContextBuilder + MemoryTool | 智能筛选上下文，管理对话记忆 |
| 持久管理层 | NoteTool | 记录任务进展、阻塞、计划，跨会话保持连贯 |

### 6.2 运行模式

| 模式 | 预处理策略 | 用途 |
|---|---|---|
| `explore` | 自动执行 find 获取项目结构 | 初次接触代码库 |
| `analyze` | 统计代码行数 + 查找 TODO/FIXME | 代码质量评估 |
| `plan` | 加载最近的 task_state 笔记 | 任务规划 |
| `auto` | 根据用户需求灵活选择 | 默认模式 |

### 6.3 自动化知识管理

自动检测代码实现详见 [[raw/2026/06/10/第九章 上下文工程#9.6.3 核心实现|源文]]（`_postprocess_response` 方法，含 blocker/action 笔记的自动创建逻辑）。

### 6.4 工作流示例

**第一天：探索** → 扫描项目结构（Flask 应用，约 50 个 Python 文件），发现数据模型问题（User.email 缺唯一约束、Order 缺时间字段），自动创建 blocker 笔记

**第二天：分析** → 统计代码质量（3542 行，测试覆盖率 45%），发现代码重复/复杂度过高/TODO 注释 12 个，批量创建 blocker

**第三天：规划** → 回顾所有 blocker 笔记，按优先级排序（高：User.email 约束 / BaseService 提取 / process_order 重构），创建详细重构计划笔记

### 6.5 扩展方向

- 集成 RAGTool 为代码库建立向量索引，结合语义检索
- 多智能体协作（探索者+分析者+规划者）
- 集成测试工具自动验证重构结果
- 通过 TerminalTool 执行 git 命令追踪代码变更
- Gradio/Streamlit 可视化界面

## 7. 核心收获

| 维度 | 要点 |
|---|---|
| 分层设计 | 即时访问(TerminalTool) + 会话记忆(MemoryTool) + 持久笔记(NoteTool) |
| 智能筛选 | 基于相关性和新近性的加权评分，贪心填充 token 预算 |
| 安全第一 | 命令白名单 + 沙箱 + 超时 + 输出限制，四层防御 |
| 人机协作 | 自动化知识管理 + 人类可通过笔记系统干预和指导 |
